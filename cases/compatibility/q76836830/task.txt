A team upgrades its Kubernetes cluster from 1.23 to 1.24, where the container runtime of the nodes is containerd and no longer Docker (dockershim is gone). The cluster pulled
its images from a Nexus Repository Manager; after the upgrade the nodes can no longer pull from it (on 1.23 they could; the same happens on Fargate, whose nodes also use
containerd). Nexus is managed behind an nginx. The thread keeps no error message and no nginx configuration. Its only answer (by the asker) says: nginx looks at the
$http_user_agent variable to send "docker" requests to the Docker repository of Nexus; after 1.24 the pull requests carry the User-Agent of containerd, which did not match,
and adding a rule for containerd to nginx.conf solved it.

Adaptation (stated on purpose): no Kubernetes, no Fargate and no Nexus run here; only the host level of one node. "Nexus" is two small stand-in programs that are already
running (do not stop, restart or replace them): its Docker repository connector (a minimal registry on 127.0.0.1:15076, plain HTTP, no authentication) and its web application
(127.0.0.1:18176: an HTML page at / and "404 Not Found" for everything else, /v2/ included). Real nginx runs in front of them at 127.0.0.1:18076 with the rule the answer
describes (reconstructed from it; the thread has not the original file). The kubelet's pull is the CRI PullImage call of the node's container runtime: here a private containerd
of its own (socket /run/bench76836830/containerd.sock, no Docker anywhere), and the node pulls the name 127.0.0.1:18076/bench76836830/app:1.0 (a loopback address, so plain HTTP).
