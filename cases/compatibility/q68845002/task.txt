On this shared Ubuntu machine a private containerd instance is the container runtime of a one-node Kubernetes-style setup. The node is started and stopped with /var/lib/bench68845002/bin/cachenodectl (cachenodectl start, stop, restart or status; it must run as root and it starts containerd with the configuration /var/lib/bench68845002/node/containerd.toml on the CRI socket /run/bench68845002/containerd.sock). The workload is a small Java program that uses Ehcache 3.9.3: it creates a cache with an off-heap resource of 50 MB, puts 1000 entries including one with the value of the environment variable NONCE, and reads them back. The workload is described by two files in /var/lib/bench68845002/workload: pod.json (the pod sandbox, with the cgroup parent that a kubelet with the systemd cgroup driver sends) and container.json (the image bench68845002.local/cache-app:jdk11.0.9, the environment NONCE=__NONCE__, a memory limit of 536870912 bytes). The command "/var/lib/bench68845002/bin/run-workload NONCE" applies them through the CRI the way a kubelet does, waits for the container, prints its log (the program first prints lines starting with probe: the JVM's total physical memory, the JVM options, the memory cgroup of the container and its memory.limit_in_bytes) and the exit code, and removes the pod; its exit code is the container's. The node's images bench68845002.local/cache-app:jdk11.0.9 and bench68845002.local/cache-app:jdk11.0.13 are the same program and the same Ehcache on JDK 11.0.9 and on JDK 11.0.13, and are already in the containerd namespace k8s.io.

The problem: the same image works when it is run with Docker, but with containerd the program fails: run-workload prints java.lang.IllegalArgumentException: Attempting to allocate 50.0MB of memory when the host only contains 0B of physical memory, and the container exits with code 1.

Your task is to find out why the JVM reports 0 bytes of physical memory in this container and to fix that cause, so that the cache is initialised, put and get work, and the JVM's total physical memory is the container's own memory limit of 536870912 bytes; and so that this still works after the node has been stopped and started again. The check restarts the node with "/var/lib/bench68845002/bin/cachenodectl restart" (it runs no other command first), runs "/var/lib/bench68845002/bin/run-workload" with a fresh nonce and expects exit code 0, "cache-ok nonce=" with that nonce and a total physical memory of 536870912 bytes in the probe lines, and then does the same once more with another nonce.

Rules: the memory limit of the container stays 536870912 bytes, the cache keeps its off-heap resource of 50 MB (the program is in the images and must not be replaced), the container has no JVM options and no JAVA_TOOL_OPTIONS or similar variables (the environment is only NONCE), and the container keeps no command and no arguments of its own (do not switch off the JVM's container support and do not hide the error); the image of the container must be one of the two images of the node; do not change cachenodectl or run-workload; pod.json may change only in the cgroup parent and container.json only in the image. Use cachenodectl, run-workload, crictl, ctr and the standard shell tools; do not use docker.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
