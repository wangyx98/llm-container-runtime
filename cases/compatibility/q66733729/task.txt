An engineer is trying out containerd with its Go client. The documentation only shows how to pull an image and make a container from it, and the engineer wants to make the container from a Dockerfile instead, like "docker build" does, from the Go program and not with the ctr tool. This machine has a containerd (socket /run/bench66733729/containerd.sock; started and stopped with /var/lib/bench66733729/bin/containerdctl) and a BuildKit daemon (socket /run/bench66733729/buildkitd.sock; buildkitctl in the same directory), whose worker is a containerd worker on that containerd; the wrappers /var/lib/bench66733729/bin/ctr and /var/lib/bench66733729/bin/buildctl are ctr and buildctl aimed at them, and you run them with sudo. The engineer's build context is /var/lib/bench66733729/demo (a Dockerfile, a static program hasher and payload.bin); the container made from its image prints a sha256 that the build wrote.

The engineer's Go program is in /var/lib/bench66733729/app (main.go and go.mod, owned by the current user): the example of the containerd documentation with the flags -context (a build context directory) and -tag (an image reference). The go of this machine is too old for these modules, so it is built with the go of this lab, a wrapper in /var/lib/bench66733729/bin/go (Go 1.24, run as the current user, not with sudo): "GOFLAGS=-mod=mod /var/lib/bench66733729/bin/go build -o app ."; it is run as root, because the containerd socket is root's: "sudo ./app -context /var/lib/bench66733729/demo -tag docker.io/library/bench66733729-app:1". It still pulls the image named by -tag, so it fails: no registry has that image.

Change the program so that it builds the Dockerfile of the -context directory and runs the result. containerd has no Dockerfile build of its own, so the build is done by the BuildKit daemon of this machine, which the program reaches with the BuildKit Go client (github.com/moby/buildkit, in go.mod at the version this daemon goes with; do not run buildctl, docker or nerdctl from the program). The program has to make the image -tag available in the containerd namespace bench66733729 (the namespace the program already uses; BuildKit's containerd worker keeps what it builds in a namespace of its own, and its configuration is not to be changed), make a container from that image in that namespace, run it with its output on the stdout of the program, and remove the container and its task when it has finished, leaving the image in place; it exits 0 when the container does. Do not pull anything and do not use an image prepared beforehand. Do not change any file in /var/lib/bench66733729/bin, /var/lib/bench66733729/etc, /var/lib/bench66733729/libexec or /var/lib/bench66733729/demo, and do not restart the daemons.
