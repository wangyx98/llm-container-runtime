A team prepares its GKE clusters for Kubernetes 1.24 (dockershim removed) and moves its Jenkins agent pods to a node pool with containerd. The agent pods used to get
access to Docker through a hostPath volume (the node's Docker socket). The asker's Spring Boot integration tests (@SpringBootTest with @Testcontainers, Testcontainers
with the Docker API) then fail at start-up; in the thread the error is

    Status 502: Bad response from Docker engine ... Could not find a valid Docker environment ... DockerClientProviderStrategy ... (docker.sock)

The asker asks how to configure a Spring Boot / Testcontainers setup to use containerd instead of Docker. An answer in the thread says that Testcontainers needs a Docker
API and does not talk to containerd; a comment says the same tests run on a desktop Docker where /var/run/docker.sock is forwarded to a Docker engine (that setup is in
the thread, the 502 is not explained there).

Adaptation (stated on purpose): no GKE, no Kubernetes, no Jenkins and no Docker Desktop run here, only the host level of one agent node. The "node" is a private mount
namespace of this machine whose /run, /etc/docker and /etc/containerd are its own, so the Docker socket of this machine is not in it. The node has a containerd (socket
/run/containerd/containerd.sock, a gRPC socket, not a Docker API) and the dockerd binary. The node's /var/run/docker.sock (= /run/docker.sock) is held by a small
"engine proxy" (a python program that is already running in the node, pid recorded): it forwards every connection to /run/docker.raw.sock and answers
"HTTP 502 Bad response from Docker engine" while nothing listens there. This layout (a docker.sock that forwards to the engine's own socket) stands in for the desktop
Docker of the thread and is the source of the exact 502 text; the real cause of the 502 on the asker's machine is not known, and this case does not claim it.
The node's /etc/docker/daemon.json is already written (cgroupfs, no bridge, no iptables; do not edit it), so containers there use no network (--network none).
The two tools of the agent's job are small wrappers in /tmp/bench76980610/bin (run them as the current user; they call sudo themselves):

    node-run COMMAND [ARGS...]     runs COMMAND inside the node
    run-test [HOLDFILE]            the test step of the job: a fixed Spring Boot test class (Spring Boot 3.1.2, Testcontainers 1.21.4, JUnit 5, started with the
                                   JUnit console launcher) that asks Testcontainers for the Docker client, loads the application image from a tar, starts a container
                                   of it through the Docker API, waits for the container's log line with a fresh nonce, checks the log, and removes the container.
                                   The JUnit summary has to say "1 tests successful" and "0 tests failed"

The job's HOME is /tmp/bench76980610/home; it is the HOME that Testcontainers reads ($HOME/.testcontainers.properties, for example docker.host=...). The environment of
the job is clean (no DOCKER_HOST), and Ryuk and the disk-space check are switched off in the wrapper because their images cannot be pulled here.

Your task is to make run-test pass in the node while the node keeps containerd as its container runtime.

Requirements:

1. After your commands, `run-test` passes: the container it starts has to be a real container in the node's containerd (the check looks for it there, and for the test's
   fresh nonce in its environment). A bare containerd socket is not a Docker API: pointing Testcontainers at /run/containerd/containerd.sock does not count, nor does
   a stand-in that only answers the first requests.
2. The Docker API has to come from a daemon that you start in the node on top of the node's containerd (dockerd of this machine). It must not start a containerd of
   its own, and it must not be the Docker of the host machine (not even through /proc/1/root or any other path to it).
3. The daemon (and the Testcontainers settings that you choose) must still be there when your script has finished: it is checked afterwards, so start it detached from your
   script (for example with setsid), and make it ready before your script ends.
4. Do not stop, restart, replace or reconfigure the node's containerd or the engine proxy; do not edit the two wrappers, the test, its jars, the image tar or the node's
   configs. Do not pull from any registry.
5. The current user has passwordless sudo; the wrappers call it themselves. Any value you need (where containerd listens, where the proxy forwards to, how dockerd is told to
   use containerd) is not given here beyond what is above; your commands must discover or decide it.
6. Your script must finish by itself: no interactive prompts, and no command that waits forever.

Return the commands needed to complete the task.
