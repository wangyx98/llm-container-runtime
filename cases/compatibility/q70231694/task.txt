This machine runs a single-node Kubernetes (k3s, node bench70231694-node) on a containerd of its own (no Docker daemon, no Docker socket). containerd and k3s are started and stopped with the scripts containerdctl and k3sctl in /var/lib/bench70231694/bin (start, stop, restart, status; run them with sudo); the same directory has kubectl (the kubectl of this Kubernetes, run with sudo). The socket of this containerd is /run/bench70231694/containerd.sock; its namespace default holds the images of the node. BuildKit v0.23.2 is installed too: buildkitd (/var/lib/bench70231694/libexec/buildkitd) runs on the host with a containerd worker on this containerd, is started and stopped with buildkitctl in the same bin directory (start, stop, restart, status), reads /var/lib/bench70231694/buildkit/buildkitd.toml and listens on /run/bench70231694/buildkit/buildkitd.sock; its client buildctl is /var/lib/bench70231694/libexec/buildctl.

An engineer used to build images in a Pod with the Docker socket mounted and wants to build with nerdctl instead. The Pod builder (namespace default, created from /var/lib/bench70231694/builder.yaml) is not privileged and runs as root. It mounts the host's directory /var/lib/bench70231694/workspace read-only on /workspace and the containerd socket of this node on /run/containerd/containerd.sock. The directory workspace is the build context: a Dockerfile (FROM localhost/bench70231694-base:1, a base image that is in containerd's namespace default; COPY payload.bin; a RUN step that writes the sha256sum of the copy to /payload.sha256) and payload.bin, 1 MiB of random bytes. The image of the Pod, bench70231694.local/builder:1, has nerdctl 2.1.3 at /home/linuxbrew/.linuxbrew/bin/nerdctl and a small shell toolset (sh, ls, cat, tar, ...).

In the Pod, nerdctl ps and nerdctl images work. nerdctl build does not:

    $ sudo /var/lib/bench70231694/bin/kubectl exec builder -- nerdctl build -t bench70231694.local/payload:1 /workspace
    time="2026-10-18T06:50:00Z" level=fatal msg="no buildkit host is available, tried 2 candidates: failed to ping to host unix:///run/buildkit-default/buildkitd.sock: exec: \"buildctl\": executable file not found in $PATH\nfailed to ping to host unix:///run/buildkit/buildkitd.sock: exec: \"buildctl\": executable file not found in $PATH"

Make nerdctl build work in the Pod builder itself, with the BuildKit of this machine: the command above has to build /workspace in the Pod and leave the image bench70231694.local/payload:1 in the namespace default of this node's containerd (nerdctl images in the Pod lists it); a container made from it has /payload.bin with the hash of the file in /workspace. Any other build context sent to the Pod's nerdctl has to work the same way. The Pod stays unprivileged and root, keeps its image and its two mounts, and must not get the host's root directory or the host's PID, network or IPC namespace. The build has to be done by this buildkitd through the Pod's nerdctl: do not build on the host in place of the Pod, do not start another BuildKit, do not move the socket of buildkitd, and do not replace or edit the programs of this machine (buildkitd, buildctl, containerd, k3s) or the configuration of containerd and k3s; a buildctl in the Pod has to be the one of this machine.

You may use kubectl, ctr, buildctl and the usual Linux tools. The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo. Return the commands needed to complete the task.
