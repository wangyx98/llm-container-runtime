An engineer runs Kubernetes workloads on CRI-O. With Docker or containerd there are Go clients that list, tag and EXPORT images (github.com/docker/docker/client, github.com/containerd/containerd); the engineer wants the same from a Go program for CRI-O: write an image of CRI-O's own store to a portable archive file. CRI-O has no such call of its own (crictl has no export or save command, and the CRI has none), and the image cannot be fetched again: it does not exist in any registry (its registry registry.bench71499683.invalid is blocked by configuration and never resolves). The image only exists in the storage of CRI-O on this machine: registry.bench71499683.invalid/shop/app:1.0 (two layers; the container prints the sha256 of a file that is unique to it).

The engineer's Go program is in /var/lib/bench71499683/app (main.go and go.mod, owned by the current user): it takes the flags -image (the image name as "sudo crictl images" shows it) and -out (the archive file to write; it must not exist yet), finds the image in CRI-O's storage through the Go libraries CRI-O itself is made of (github.com/containers/image/v5, with github.com/containers/storage below it; go.mod pins the versions of CRI-O 1.34 for both), prints its config digest, and then stops with "not implemented": nothing is exported. It is built with the go of this lab, a wrapper in /var/lib/bench71499683/bin/go (Go 1.24, run as the current user, not with sudo; the go of this machine is too old; the wrapper sets the build tags that leave out the parts of the libraries that need gpgme, btrfs and devicemapper headers): "/var/lib/bench71499683/bin/go build -o app ."; it is run as root, because the storage is root's: "sudo ./app -image registry.bench71499683.invalid/shop/app:1.0 -out /tmp/bench71499683/shop-app.tar".

Change the program so that it exports the image given by -image from the storage of CRI-O into the archive file given by -out, itself, through these Go libraries (containers/storage, the store itself, and/or containers/image/v5 on top of it: the Go API of the storage; do not run skopeo, podman, buildah, crictl, docker or any other program from it). The archive has to be an image archive of that image (docker-archive or oci-archive, your choice): its config says what the config of the image says, its layers are the two layers of the image with the unique file in them, with no registry involved: not a listing of the image, not the files of a root file system, not a re-pull. The source image has to stay in CRI-O's store, usable. Do not change any file in /var/lib/bench71499683/bin or /etc/containers, and do not restart CRI-O.

The check builds your program itself with that go and runs it twice as root, on this image and on a new image (another name, another unique file) that it puts into CRI-O's storage for the purpose: it expects exit 0, no other program started by yours, an archive whose config and layers are those of that image (a docker-archive keeps the config byte for byte; an oci-archive has a converted one: the check compares what it says) and which a clean store of its own can load and run (printing the unique file's sha256), and both images still in CRI-O's store.

You may use go, crictl, podman (as a tool to look at the store, not as the exporter) and the usual Linux tools; the Go modules are fetched by go as usual and are already in its cache. The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo (that go runs as the current user). Return the commands needed to complete the task, including the content of the Go files you write (for example with cat > main.go <<'EOF' ... EOF).
