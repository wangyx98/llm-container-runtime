On this shared Ubuntu machine a small container node is modelled on the question "Is there any programmatic way to detect that a process running under containerd has its stdin and stdout closed?": a process is started in a container with kubectl exec (-i, or -it with a terminal); the client on the other side (kubectl) is killed, and the process in the container goes on as if nothing had happened. It is never told that its session is gone, and the question asks how a process can find out by itself.

The node is a private containerd 1.7.20 with the CRI plugin (CRI socket /run/bench78687277/containerd.sock; its files are below /var/lib/bench78687277 and /run/bench78687277; the machine's own containerd, crictl and runc are not the node's). The commands are /var/lib/bench78687277/bin/nodectl start|stop|restart|status and /var/lib/bench78687277/bin/crictl (crictl for the node's socket), both with sudo. One pod, main, runs on the network of the node; in it the container app (pid 1: /bin/idle, which sleeps for ever) is Running. The image of app is a single static program with a few links: it has no shell, no libc and no interpreter. Three host directories are mounted in app: /probe (the host directory /var/lib/bench78687277/probe, read-only in the container, writable on the host), /lab (read-only, the lab's own files) and /out (the host directory /run/bench78687277/out, read-write). Nothing has to be pulled from the internet.

The sessions are the CRI's exec streams, the ones kubelet serves to kubectl exec, and the lab runs them with crictl: `crictl exec -i [-t] app-container-ID COMMAND...`. Two kinds of session occur. Without -t the client has pipes: its stdin is a pipe that stays open and is silent as long as the client lives, and what the process writes is read and thrown away. With -t the client runs on a terminal, and the "person" at it is a real terminal emulator: it displays what the process writes, and it answers the standard queries a terminal answers (the cursor position report, for one) the way xterm does. Clients end the way kubectl ends when it is killed or loses its connection: they are killed with SIGKILL, or terminated with SIGTERM. The container app itself must go on running.

Your task: write a program that a process can run inside the container, so that it learns that its exec session is over, and says so. The program is the static executable /var/lib/bench78687277/probe/detect (/probe/detect in the container); gcc is installed on the host, the executable must be static. The check starts it as `/probe/detect TOKEN` (TOKEN, one argument, is a different string in every session) in sessions of both kinds, side by side, and then ends some of the clients:
 - when the client of a session is gone, the program of that session reports it, exactly once, within 8 seconds of the end of the client, and not before: it connects to the unix socket /out/events.sock (a stream socket the check opens during its run; it does not exist before) and sends one line, TOKEN followed by a newline. The report has to be made by the process /probe/detect TOKEN itself, not by one of its children and not by something outside the container: the check asks the kernel who connected. After it has reported the program may end;
 - while the client of a session is connected the program reports nothing, whether the session has a terminal or not, however long it lasts (the longest session lasts more than 20 seconds), and it keeps running;
 - it writes at most 2 KB in all to its session (a person is looking at that terminal).
The lab's own files (the node's programs and configuration, the pod's and the container's definitions, the tools in bin) stay as they are, and the node's containerd and the container app must keep running; the program has to be put in place with the files of the lab left alone, not by changing the node. Use the node's tools, crictl, gcc and the standard shell tools; do not use docker or podman.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
