On this shared Ubuntu machine a small cell is modelled on the question "How to get into an App Container Manually with Garden-RunC Backend": on a Cloud Foundry diego-cell the asker wants a shell in the container of an app instance with `runc exec` (he does not want `cf ssh`); `cfdot` lists the instance and its directory exists in Garden's depot, but `runc exec <instance guid>` says `container does not exist` and `runc list` shows nothing. The only answer says to use Garden's own client (gaol) and does not answer the runc question. What follows is an adaptation, and not a real Cloud Foundry: no Garden (gdn) runs here. The cell is a set of bare runc containers laid out like a Garden cell, with a stand-in for cfdot.

The cell's files are below /var/lib/bench56751319 and /run/bench56751319. The runc of the cell is /var/lib/bench56751319/packages/runc/bin/runc (like /var/vcap/packages/runc/bin/runc; runc 1.1.12; use it with sudo). The depot is /var/lib/bench56751319/data/garden/depot (one directory per container, named like its handle, holding the bundle). `sudo /var/lib/bench56751319/bin/cfdot actual-lrps` lists the app instances, one JSON object per line, with the instance_guid; the instance guid is the container's handle and the id runc knows it by. The containers run a tiny program (commands init, cat, ls, id; there is no shell in them). `sudo /var/lib/bench56751319/bin/newcell` creates another instance like them (it prints the guid; `--fresh-root` makes the new one in a runc root of its own, as another cell of the same kind could have). Each container has a file /tmp/rXXXXXXXX.txt that exists only inside it.

Your task: write the tool /var/lib/bench56751319/gexec (an executable run with sudo, with TWO arguments: an instance guid and the path of a file in that container; its stdout is ONE JSON object). It finds how the instance can be reached with the runc of the cell and reads the file inside the container with `runc exec`, and reports:
- "instance_guid": the guid it was given;
- "handle": the handle (the id) under which runc knows that container;
- "runc_root": the runc root (the directory given with --root) below which runc keeps that container;
- "init_pid": the pid, as the cell sees it, of the container's init process (the one runc reports for the container);
- "content": the content of the file, without the final newline.
The tool is run later for containers that did not exist when it was written, some of them in another runc root, and what it prints must be right for them: nothing may be written into the tool from what is true today. The tool may use only the runc of the cell (/var/lib/bench56751319/packages/runc/bin/runc) to look at and to reach the container, must not start, stop, restart or delete any container, must leave the container's processes as they are (the exec'ed process ends, nothing stays behind), must not call docker, podman or gaol, must finish within 60 seconds, and must not change the cell's files, its depot or the default runc root (/run/runc).

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
