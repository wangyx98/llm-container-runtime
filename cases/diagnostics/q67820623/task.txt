On this shared Ubuntu machine a small container node is modelled on the question "Containerd pull multiple images while creating a Pod in Kubernetes": a node whose runtime is containerd lists, for ONE image the kubelet pulled, three images (`ctr -n k8s.io images ls`: `name:tag`, `name@sha256:<manifest digest>` and `sha256:<config digest>`, all with the same manifest digest and size), the events show two `/images/create`, and the asker, who expects one image, fears that every Pod makes the node pull and store the image again until the disk is under pressure. The thread's only answer says the tag is resolved to the digest first and nothing is downloaded twice, but it measures nothing and says nothing about the disk. What follows is an adaptation: the lab measures it.

The node is a private containerd 1.6.17 with the CRI plugin and runc v1.1.12; the images come from a REAL registry (distribution 2.8.3, plain HTTP on 127.0.0.1:5067, repositories bench/a, bench/b, bench/pause; bench/a has the tags 1 and 2 that point at the same manifest; bench/a and bench/b share a 2 MiB base layer and the layer with the program, and each has a 1 MiB layer of its own). Every request the registry gets is one line of its access log /run/bench67820623/registry.log (Apache combined format: `<ip> - - [<time>] "<METHOD> <path> HTTP/1.1" <status> <bytes sent> "<referer>" "<user agent>"`). The node's files are below /var/lib/bench67820623 and /run/bench67820623 (the machine's own containerd, crictl, runc and docker/podman are not the node's). The commands are /var/lib/bench67820623/bin/nodectl, /var/lib/bench67820623/bin/crictl and /var/lib/bench67820623/bin/ctr (ctr for the node's socket, in the namespace k8s.io), all with sudo; the configuration is /var/lib/bench67820623/etc/containerd.toml, the content store /var/lib/bench67820623/containerd/io.containerd.content.v1.content, the snapshotter's data /var/lib/bench67820623/containerd/io.containerd.snapshotter.v1.overlayfs. The pods' definitions are in /var/lib/bench67820623/pods. The node has pulled the sandbox image bench/pause:1 and bench/a:1 through the CRI and runs two pods of bench/a:1 whose programs write 1 MiB and 2 MiB into their own writable layers. The registry's log has the pulls so far.

Your task: write the read-only tool /var/lib/bench67820623/imgreport (an executable that is run with sudo, no arguments, and prints ONE JSON object on stdout) that measures the node and the registry's log and tells the asker what is stored, what was transferred and what grows. The fields, all measured when the tool runs:
- "records": an object, every record of ctr's list for the namespace k8s.io (its name) -> the manifest digest it points at;
- "blobs": {"count": number of blobs in the node's content store (the files under the content store's blobs directory), "bytes": the sum of their sizes};
- "snapshots": {"committed": number of committed snapshots, "active": number of active snapshots} (ctr snapshots ls, all keys);
- "containers": an object, every container record of k8s.io (ctr containers ls, sandboxes included) -> {"image": the image name of the record, "rw_bytes": the sum of the sizes of the REGULAR FILES in the upper directory of the container's active snapshot (its key is the container's snapshot key)};
- "registry": counts over every line of the registry's access log with status 200: "blob_gets" and "blob_bytes" (GET of a path with /blobs/, number of lines and the sum of the bytes sent), "manifest_gets" (GET of a path with /manifests/) and "manifest_heads" (HEAD of a path with /manifests/).
The tool is run again later, after the node has been changed (another tag of an image pulled, another image that shares layers pulled, another Pod created), and what it prints must be right then: nothing may be written into the tool from what is true today. The tool must not change anything: it creates and removes no record, blob, snapshot, container or pod, pulls nothing, does not call the registry and does not write its log; it may not call docker or podman; it has to finish within 60 seconds. Do not change the node's or the registry's configuration, programs or data.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
