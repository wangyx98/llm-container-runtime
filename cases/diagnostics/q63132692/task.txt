On this shared Ubuntu machine a small container node is modelled on the question "Unable to fetch cpu pod metrics, k8s - containerd - containerd-shim-runsc-v1 - gvisor": a private containerd with the CRI (socket /run/bench63132692/containerd.sock; its files below /var/lib/bench63132692 and /run/bench63132692) runs pods with two runtime handlers, runc (the default) and runsc (gVisor, through the shim io.containerd.runsc.v1). The node has no kubelet and no metrics-server: its statistics are read from the CRI (crictl stats) and from containerd (ctr -n k8s.io tasks metrics CONTAINER_ID). The commands for the node are /var/lib/bench63132692/bin/crictl (crictl for the node's socket) and /var/lib/bench63132692/bin/nodectl start|stop|restart|status (the node's containerd), both with sudo; the machine's own containerd, ctr and crictl configuration are not the node's. Nothing has to be pulled from the internet: the images are on the node, and every gVisor release that may be used is on the disk.

The node's containerd finds containerd-shim-runsc-v1 and runsc in /var/lib/bench63132692/node/bin (first in its PATH; a symbolic link each). The gVisor releases that the machine has are /var/lib/bench63132692/releases/RELEASE/runsc (RELEASE is the date of the release); the shim is one build whatever the runsc. The definitions of the three pods are in /var/lib/bench63132692/pods: NAME.pod.json for crictl runp, NAME.ctr.json for crictl create, with a --runtime runsc or runc as the pod needs. The pods are gv-busy (runtime handler runsc, runs /bin/spin: one busy loop, one CPU), gv-idle (runsc, runs /bin/idle: sleeps) and rc-busy (runc, runs /bin/spin, the control). All three use the network of the node and need none.

The situation, as in the question: the busy runc pod rc-busy reports its CPU, the gVisor pods report their memory, but their CPU counter stays 0 whatever they do (crictl stats shows a CPU of 0 for gv-busy although it uses a core; ctr shows the same). An autoscaler built on these numbers would never scale the gVisor pod.

Your task: make the two gVisor pods report their own CPU, at both layers (CRI and containerd): gv-busy must show a CPU counter that grows at about one core (it uses one), gv-idle almost nothing. The numbers have to be the pods' own: a counter that is not 0 but belongs to something else (a larger group, the node, another pod) is no answer. The pods must still run in gVisor.

Rules: the pods keep their names and definitions (the files in /var/lib/bench63132692/pods are not changed), gv-busy and gv-idle keep the runtime handler runsc and their programs, rc-busy is not touched (the check compares its IDs), the node has exactly these three pods when you finish, and the lab's files stay as they are (the pods' definitions, containerd's and runsc's configuration files, the shim, the files of the releases, the tools); runsc has to be a file of one of the releases on the disk (no wrapper, no other binary). Do not write numbers by hand: the check reads the counters of the two layers itself, twice, a few seconds apart. Use crictl, ctr, the node's tools and the standard shell tools; do not use docker, nerdctl or kubectl.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
