On this shared Ubuntu machine a small Kubernetes-style node is modelled on the question "Kubernetes fails to pull images from gitlab registry unknown-sha256: <4ca..252> unexpected commit digest precondition": a containerd node (the kubelet's CRI) must pull an image from the container registry of a GitLab host, and every pull ends with `rpc error: code = FailedPrecondition desc = failed to pull and unpack image "10.68.63.45:5050/lab-user/webapp/nginx:v1": failed commit on ref "unknown-sha256:<D1>": unexpected commit digest sha256:<D2>, expected sha256:<D1>: failed precondition` (D1 and D2 are two different digests). On the asker's side `docker login` and `docker pull` from another server work, and `ctr image pull` works on the node. Nothing in the question says why. This lab is NOT a GitLab product: the GitLab host is modelled by 10.68.63.45 (an alias of the loopback interface), with the real container registry (distribution 2.8.3) on https port 5050 and a stand-in for the web application on https port 443, both with the certificate of the lab's CA /var/lib/bench68630845/pki/ca.crt; the registry authenticates with Bearer tokens that the web application issues at https://10.68.63.45/jwt/auth, and its project is lab-user/webapp.

The node is a private containerd 1.6.17 with the CRI plugin (CRI socket /run/bench68630845/containerd.sock; its files are below /var/lib/bench68630845 and /run/bench68630845; the machine's own containerd, crictl and runc are not the node's). Its configuration, /var/lib/bench68630845/etc/containerd.toml (read when containerd starts), has the registry settings of the question: the lab's CA for the host and for the host with the port, and a mirror entry for 10.68.63.45:5050. The commands are /var/lib/bench68630845/bin/nodectl start|stop|restart|status, /var/lib/bench68630845/bin/crictl (crictl for the node's socket) and /var/lib/bench68630845/bin/ctr (ctr for the node's socket), all with sudo. What the kubelet does with the pull secret (a GitLab deploy token) is `sudo /var/lib/bench68630845/bin/crictl pull --creds 'gitlab+deploy-token-1:k8s-pull-secret' 10.68.63.45:5050/lab-user/webapp/nginx:v1`; for ctr it is `sudo /var/lib/bench68630845/bin/ctr -n NAME images pull --tlscacert /var/lib/bench68630845/pki/ca.crt --user 'gitlab+deploy-token-1:k8s-pull-secret' 10.68.63.45:5050/lab-user/webapp/nginx:v1`. The logs of the two servers are /run/bench68630845/registry.log and /run/bench68630845/web.log (the web application writes one JSON line per request, with the sha256 of the body of a 200). Nothing has to be pulled from the internet.

Your task: find out why the node's pull fails with `unexpected commit digest` and make the node pull the image through the CRI. The check removes the image, pulls it again with the command above and starts a pod with it: the pull must succeed and give the digest of the image in the registry, the requests of the pull must go to the registry (the web application may only be asked for tokens), and the container must run and print the token that is baked into the image. The solution has to keep working when containerd is restarted with nodectl: the lab's files, that is the registry and its data, the web application, the certificates, the node's programs and the pod's definition, stay as they are; containerd.toml and the restart of containerd are for you. Use the lab's tools, curl, python3 and the standard shell tools; do not use docker or podman.
