This machine runs a small Kubernetes-style node of its own for this exercise: a containerd (the node's container runtime, with its CRI; socket /run/bench68684356/containerd.sock)
and a kubelet that runs three pods from static pod manifests. There is no API server and no cluster. The machine's own container tools are not touched. Two wrappers:

    /tmp/bench68684356/bin/node-ctl status        # the node = this containerd + this kubelet
    /tmp/bench68684356/bin/node-crictl            # crictl of this containerd (it calls sudo itself)

(Adaptation: the question is about a Go program on a K8s/K3s node that has to know whether a pod is really ready, without the API server and straight from the runtime. This
exercise is that node, reduced to what the question talks about: the runtime and the kubelet next to a client program, with the readiness probes of the pods.)

The three pods (namespace bench, host network, one container each) are named as the kubelet names static pods, <name>-<node>: gate-node1, steady-node1 and never-node1. Each has
an exec readiness probe (every 3 s; two failures in a row make the pod NotReady):

    gate    the probe follows the file /var/lib/bench68684356/gate/open (a test opens and closes the gate: the pod turns Ready and NotReady with it), but only after the file has
            been in the same state (present or absent) for 3 s: a gate that is opened or closed for a shorter time changes nothing
    steady  the probe always passes
    never   the probe always fails

    $ /tmp/bench68684356/bin/node-crictl pods ; /tmp/bench68684356/bin/node-crictl ps
    (all three sandboxes are Ready and all three containers Running, whatever the readiness probes say)

Your task: make the command /tmp/bench68684356/bin/pod-ready (an executable program or script, any language; the machine has python3). `pod-ready POD` prints true or false and exits
with 0: whether the pod POD (its name as above) is Ready as the node judges it with its readiness probe. For a pod the node does not have it exits with a non-zero status and prints
neither true nor false. The kubelet's configuration is /var/lib/bench68684356/kubelet/config.yaml.

Requirements:

1. pod-ready is called by itself many times while gate is opened and closed. Each answer is what the kubelet has judged at that moment (a change may take up to 1.8 s to show). A gate that
   is open (or closed) for only 2 s does not change the readiness of the pod: the answer follows the pod's readiness as the kubelet judges it, not the gate file and not the state of
   the containers or sandboxes.
2. The answer comes from the node: no API server is started or faked, no answer is written down in advance, nothing is cached between calls that could go stale.
3. The node stays as it is: files, kubelet configuration, manifests and probes unchanged; the same containerd and kubelet processes; the same three sandboxes and containers (the pods are
   not recreated or restarted). The gate is the test's: do not open or close it.
4. No download. A command you start with a shell keeps the pipes of that shell open unless you redirect its output.

Use sudo for the node's files if you need it.
