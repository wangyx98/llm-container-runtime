On this shared Ubuntu machine a small container node is modelled on the question "failed to unpack image on snapshotter overlayfs: unexpected media type text/html": a Kubernetes node (containerd v1.6.17) cannot pull an image from a private Harbor (v2.5.5, HTTPS, a project that needs an account) although the registry settings of containerd have the CA file and the account. kubelet shows ErrImagePull with `failed to pull and unpack image "...": failed to unpack image on snapshotter overlayfs: unexpected media type text/html for sha256:<digest>: not found`. The thread of the question did not keep a single HTTP response, and its answer ("trust the CA") does not fit an error that is not a certificate error; what the registry really sent has to be found out.

This lab is a controlled stand-in, not a Harbor: a small program in front of the registry data answers with the routes of a Harbor 2.5 and nothing else of it. https://10.75.62.29:8443/v2/ is the registry API (Bearer tokens: an anonymous client gets 401 and the address of the token service), /service/token is the token service (it checks the account admin / Harbor12345), and every other path is the page of the portal, answered "200 text/html" like the single page application of a Harbor does for any path. The registry's certificate is signed by the lab's CA (/var/lib/bench75622952/pki/ca.crt, 10.75.62.29 is in it). The registry's log, one JSON line per request with its path, status, Content-Type, kind of authorization and User-Agent, is /run/bench75622952/front.log. The image is 10.75.62.29:8443/k8mtest/k8m:v1.0, one static program that prints a token every two seconds. Nothing has to be pulled from the internet.

The node is a private containerd 1.6.17 with the CRI plugin (socket /run/bench75622952/containerd.sock; its files are below /var/lib/bench75622952 and /run/bench75622952; the machine's own containerd, crictl and runc are not the node's). The commands are /var/lib/bench75622952/bin/nodectl start|stop|restart|status and /var/lib/bench75622952/bin/crictl (crictl for the node's socket), both with sudo; there is also bin/ctr for the node. The node's configuration is /var/lib/bench75622952/etc/containerd.toml, read when containerd starts. It has the registry settings of the question: for 10.75.62.29:8443 the CA file, `insecure_skip_verify = false`, the account admin / Harbor12345, and a mirror with the endpoint "https://10.75.62.29:8443/". The pod's and the container's definitions are /var/lib/bench75622952/pods/pod.json and ctr.json (a pod on the network of the node, one container of the image). Today `sudo /var/lib/bench75622952/bin/crictl pull 10.75.62.29:8443/k8mtest/k8m:v1.0` fails with the error of the question.

Your task: find out why the node is given text/html (look at what the node asks the registry and what it gets, in the registry's log) and make the node pull the image through the CRI and run it, so that it keeps working after containerd is restarted. The check removes the pods and the image, pulls the image cold through the CRI (the manifest must be the registry's, with the digest the registry gives), checks in the registry's log how the node asked (authenticated, as a registry client), and starts the pod and the container, which must print the token of the image. Then it lets the registry show a second certificate for the same name, signed by a CA nobody trusts: a pull of the image must still fail then, on the certificate. And the registry must still give its manifest only to a client with a token. So the fix may not skip, weaken or bypass the verification or the authentication: not `insecure_skip_verify`, not a changed registry or certificate, not the machine's trust store (/etc/ssl/certs), and not an image put into the node by other means than the pull. The lab's own files (the registry program and its certificates and image data, the node's programs, the pod's definitions, the tools in bin) stay as they are, and the node must be the node's containerd v1.6.17. Use the node's tools, curl, the standard shell tools; do not use docker or podman.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
