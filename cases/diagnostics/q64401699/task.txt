On this shared Ubuntu machine a small container node is modelled on the question "microk8s containerd - failed to reserve sandbox name": on a MicroK8s node (a Raspberry Pi) the containerd service does not start any more and the node stays NotReady; its journal ends with `level=fatal msg="Failed to run CRI service" error="failed to recover state: failed to reserve sandbox name \"<pod>_<namespace>_<uid>_<attempt>\": name ... is reserved for \"<id>\""`. `microk8s stop/start` and `microk8s reset` change nothing, and `ctr containers info <id>` for the id in the message says "not found" (containerd is not running, so ctr cannot answer anything). The thread's own answer moves the whole containerd data directory away, which gives a node with no images and no pods: that is a rebuild, not a repair. The real store of the question was not kept, so what follows is an adaptation: in the lab a pod has two sandbox records after a hard reset; it is not a claim about what happened on the asker's node.

The node is a private containerd 1.6.17 with the CRI plugin and runc v1.1.12 (MicroK8s 1.18/1.19 ship containerd 1.3/1.4, which have no arm64 build; the CRI plugin's recovery is the same code). Its files are below /var/lib/bench64401699 and /run/bench64401699 (the machine's own containerd, crictl, runc and docker/podman are not the node's). The commands are /var/lib/bench64401699/bin/nodectl start|stop|restart|status, /var/lib/bench64401699/bin/crictl and /var/lib/bench64401699/bin/ctr (crictl and ctr for the node's socket; the CRI's namespace is k8s.io), all with sudo. The configuration is /var/lib/bench64401699/etc/containerd.toml (read when containerd starts; root /var/lib/bench64401699/containerd; the log is /run/bench64401699/containerd.log). The pods' definitions are in /var/lib/bench64401699/pods (host-network pods). The node held two images, a pod "web" (namespace cert-manager, attempt 3, with a container) and an unrelated pod "other" (namespace kube-system, with a container); all of them were running when the host was reset hard: the processes, /run and the mounts are gone, the files below /var/lib are as the disk has them. After the reset the pod "web" has two sandbox records in the namespace k8s.io. Today `sudo /var/lib/bench64401699/bin/nodectl start` fails with the message of the question.

Your task: make the node's containerd, with its CRI plugin, start again with what it knew, and the node serve the CRI. Nothing the node knew may be thrown away except the duplicate: both images, the pod "other" and its container, and the pod "web" with its container must still be listed by crictl under their ids; of the two sandbox records of "web" the one to keep is the real one - the sandbox whose snapshot exists and which the container of the pod belongs to - and the other must be gone (the id in the error message is only the one the plugin loaded first). Deleting or moving the node's root, the images, the snapshots or the pods is not the repair. Afterwards the node must create a new sandbox: the check runs the next attempt of the pod "web" (pods/web-next.json) with a container, which must run and print its token, then restarts the node's containerd and looks at everything again. The configuration file must be as it is now when you are done (CRI plugin enabled, same root and sockets); the node must be the lab's containerd v1.6.17 started with it.

Use the node's tools, python3, the standard shell tools; do not replace the node's programs, do not use docker or podman, and do not touch the machine's own containerd.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
