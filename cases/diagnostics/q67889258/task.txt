On this shared Ubuntu machine a small container node is modelled on the question "Docker service doesn't start after hard host reboot": after a hard reset of the host the system containerd does not start any more, it ends with a Go panic in the bbolt library, in the metadata plugin (`slice bounds out of range ... bbolt.(*leafPageElement).key ... bbolt.(*Cursor).nsearch ... metadata.(*DB).Init`), and reinstalling the packages does not help (they do not touch the data). Docker's own containerd, which dockerd starts with another root, still runs. The thread of the question has no answer and no comment, so what follows is an adaptation: the lab shows one concrete way this file gets torn and one way to get the daemon back without losing what it knew; it is not a claim about what happened on the asker's host.

The node is a private containerd 1.6.17 (the question's 1.4.6 has no arm64 build; the metadata plugin and bbolt fail the same way) with runc v1.1.12 and no CRI plugin. Its files are below /var/lib/bench67889258 and /run/bench67889258 (the machine's own containerd, runc and docker/podman are not the node's). The commands are /var/lib/bench67889258/bin/nodectl start|stop|restart|status and /var/lib/bench67889258/bin/ctr (ctr for the node's socket, in the namespace "bench"), both with sudo. The configuration is /var/lib/bench67889258/etc/containerd.toml (root /var/lib/bench67889258/containerd). The metadata database is /var/lib/bench67889258/containerd/io.containerd.metadata.v1.bolt/meta.db. The OCI archive from which the image was once imported is /var/lib/bench67889258/image/app.tar.

Before the power failed the node held one image, bench67889258.local/app:1, and one container c1 (with the label bench.token) that had been running a small program: it writes /marker once, when it first starts, and /beat every second, in the container's own writable layer (the snapshot c1). The host was reset hard while containerd was writing: processes, /run and the mounts are gone, the files below /var/lib are as the disk has them. Today `sudo /var/lib/bench67889258/bin/nodectl start` fails with the panic of the question; see /run/bench67889258/containerd.log.

Your task: make the node's containerd start again with what it knew, and the workload runnable. The image and the container c1 must be the original ones: the same image digest, the same container record (creation time and label bench.token), the same writable snapshot with the /marker the program wrote - a container made anew with the same name, or an image imported again, is not the original; deleting the database or the data directories is not the repair. What may be lost is only the last transaction that was being committed when the power failed (it cannot be known from the file alone; a label the node wrote last is the kind of thing meant), and nothing else. The broken meta.db must be kept as evidence, unchanged byte for byte: put a copy of it, before you touch the file, into the directory /var/lib/bench67889258/evidence/ (any file name). The check starts the task of c1 (the program must write /beat with the token of c1, and /marker must still have it), restarts the node's containerd and looks again.

Use the node's tools, python3, the standard shell tools; do not replace the node's programs or configuration (containerd.toml stays as it is, the node must be the lab's containerd 1.6.17), do not use docker or podman, and do not touch the machine's own containerd.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
