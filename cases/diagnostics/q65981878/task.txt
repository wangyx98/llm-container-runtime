On this shared Ubuntu machine a small container node is modelled on the question "How to get more information for an error generated in libcontainer/rootfs_linux.go?": a container fails to start with the error that runc's prepareRootfs makes when a mount fails (`mounting %q to rootfs at %q`), it happened once, and the asker, who is not interested in why it happened but in how to get more information from that function, edited runc's source (fmt.Printf at the start of prepareRootfs, another error constructor) and sees none of it. The thread has no answer. What follows is an adaptation: a diagnostic task whose answer is measured on the lab's runs.

The node is a private containerd 1.6.17 with the CRI plugin and runc v1.1.12 (CRI socket /run/bench65981878/containerd.sock; its files are below /var/lib/bench65981878 and /run/bench65981878; the machine's own containerd, crictl and runc are not the node's). The commands are /var/lib/bench65981878/bin/nodectl, /var/lib/bench65981878/bin/crictl (the node's socket; note that its default timeout is short) and /var/lib/bench65981878/bin/ctr (namespace k8s.io), all with sudo; strace is installed. The program that containerd's shim runs for a container is the file called runc that it finds in the PATH of the node (the lab's runc is in /var/lib/bench65981878/node/bin); a runc "rebuilt" by someone else is in /var/lib/bench65981878/patched/runc, a directory the node does not use. The pod lab (host network) runs. The container whose id is in /var/lib/bench65981878/bad.cid is in the state Created in it; `sudo /var/lib/bench65981878/bin/newbad` creates another one like it in the pod lab (it prints the container id; every call makes other host files, other names and another bad mount, and each container is Created and has NOT been started): each has a few thousand bind mounts that work and ONE that cannot (a directory onto a file or a file onto a directory, somewhere below /m), and `crictl start` of it fails inside runc's init, in prepareRootfs. A container can be started once.

Your task: write the tool /var/lib/bench65981878/mountfail (an executable run with sudo, with ONE argument, the id of a Created container of the pod lab; its stdout is ONE JSON object). The tool starts that container (it fails) and reports, from what really happened in that run:
- "container": the id it was given;
- "mount": {"source": the host path of the mount that failed; "destination": its path in the container; "flags": the integer that runc prints as `flags: 0x...` for it; "errno": the symbolic name of the error of the failing mount(2) of that mount (for example "ENOENT"); "errno_num": its number};
- "init_pid": the pid, as the node sees it (not a pid in the container), of the process that issued that failing mount(2): the runc init of that run, the process that executes prepareRootfs;
- "runc": {"path": the path of the runc file that the shim executed for this container; "sha256": the sha256 of that file}.
The tool is run again later, for other containers that did not exist when it was written, and what it prints must be right for them: nothing may be written into the tool from what is true today. The tool must run only the start of the given container (no other container may be started by it, no runc started on its own account), must finish within 120 seconds, may not call docker or podman, and must not change the node's or the pod's definitions, programs or configuration (the lab's runc, configuration and tools stay as they are; nothing is rebuilt into the node).

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
