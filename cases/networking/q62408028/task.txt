kubelet fails to create the pod sandbox for coredns under CRI-O, with:

    RunPodSandbox from runtime service failed: rpc error: code = Unknown
    desc = failed to create pod network sandbox ...: failed to set bridge
    addr: could not add IP address to "cni0": permission denied

The asker eventually fixed it themselves and explained the real root
cause in their own accepted answer: their CNI bridge conflist
(/etc/cni/net.d/*.conflist, the file CRI-O ships with a default subnet
like 10.85.0.0/16) did NOT match the pod-network subnet their cluster
was actually supposed to use (Flannel's default, 10.244.0.0/16, and in
their case actually a /24). The "cni0" Linux bridge device had ALREADY
been created on the host -- by an earlier kubeadm/CNI-plugin attempt --
with the OLD subnet's gateway address already assigned to it. When the
CNI bridge plugin later runs again with a conflicting netconf, it
refuses to touch the bridge's address and fails outright. As the asker
put it, once they actually looked at the logs they found the real
underlying error the permission-denied one was masking:

    failed to set bridge addr: "cni0" already has an IP address
    different from 10.244.0.1/24

This benchmark reproduces that EXACT underlying mechanism directly at
the CNI plugin level -- the same `bridge` + `host-local` CNI plugins
that CRI-O invokes on kubelet's behalf -- instead of standing up a full
kubeadm + kubelet + Flannel/Calico cluster, since the cluster machinery
above it is not what's actually broken.

  - A "cni0" Linux bridge that ALREADY EXISTS on the host, left over
    from an earlier (unrelated) pod attachment, with an IPv4 address in

  - The CURRENT, intended netconf at /tmp/bench62408028/netconf.json,

  - An empty, unattached network namespace at

runtime does: set the environment variables CNI_COMMAND=ADD,
CNI_CONTAINERID=<some id>, CNI_NETNS=<netns path>, CNI_IFNAME=eth0,
CNI_PATH=/tmp/bench62408028/cni-bin, then run
/tmp/bench62408028/cni-bin/bridge with the netconf JSON on stdin.
