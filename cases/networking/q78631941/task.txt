On this shared Ubuntu machine a Go program pulls an image and runs a container from it with the containerd Go client and the SOCI snapshotter (lazy loading: the layers of the image are mounted through FUSE by the snapshotter and read from the registry when the container reads them). The Go program is in /tmp/bench78631941/app (main.go and go.mod, built with `GOFLAGS=-mod=mod go build -o lazyrun .` in that directory, using the client github.com/containerd/containerd/v2 at version v2.0.5; the Go modules are downloaded on the first build, and the program is built already). It is started like this (as root: the client mounts the snapshot of the container):

    sudo ./lazyrun --address /run/bench78631941/containerd.sock --namespace bench78631941 --name lazy --ref 10.78.63.2:5000/app:seed --snapshotter soci

It pulls the image with a resolver for plain HTTP (the registry speaks HTTP only), unpacks it with the snapshotter soci, creates the container lazy from it (its process is /reader hold) and starts it. The container lazy is running now, made by this program. To run a command in it, for example: sudo ctr -a /run/bench78631941/containerd.sock -n bench78631941 tasks exec --exec-id e1 lazy /reader sha256 /data/d00/sub/x00/f00.bin (it prints the sha256 and the size of that file of the image).

The problem: the pull and the container work, but the layer is not lazy-loaded. The snapshotter's log (/var/lib/bench78631941/soci/soci.log) shows that it failed to prepare a remote snapshot, with the error http: server gave HTTP response to HTTPS client, then containerd downloads the whole layer itself and unpacks it locally: there is no FUSE mount of the snapshotter, and the registry sees the layer fetched whole.

What the machine has: a private containerd (socket /run/bench78631941/containerd.sock, its own root) with the proxy snapshotter soci, which is the SOCI snapshotter v0.16.1 (socket /run/bench78631941/soci.sock). The snapshotter is a service of the machine: sudo /var/lib/bench78631941/bin/soci-service start, stop, restart or status. Its configuration is /var/lib/bench78631941/soci/config.toml (read when it starts), its root is /var/lib/bench78631941/soci/root (the FUSE mounts of lazy-loaded layers are below it). The registry is at 10.78.63.2:5000, plain HTTP, no TLS, no authentication. Its image app:seed has one gzip layer of about 48 MiB that holds /reader and twelve files of 4 MiB at /data/dNN/sub/xNN/fNN.bin (NN = 00 to 11), and the registry also holds the SOCI index and the ztoc of that layer: they are valid, the image was converted for SOCI.

Your task is to make the container that the program creates from an image of the registry use the SOCI snapshotter as it is meant to be used: the layer is mounted through FUSE by the snapshotter, and the snapshotter itself reads from the registry, over plain HTTP, the index, the ztoc and the parts of the layer that the container reads.
