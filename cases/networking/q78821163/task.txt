On this shared Ubuntu machine an application starts a Docker-in-Docker container with the containerd Go client. The Go program is in /tmp/bench78821163/app (main.go and go.mod, built with `GOFLAGS=-mod=mod go build -o dind .` in that directory, using the client github.com/containerd/containerd/v2 at version v2.0.5; the Go modules are downloaded on the first build, and the program is built already). It is started like this (as root: the client mounts the snapshot of the image to read its configuration):

    sudo ./dind --address /run/bench78821163/containerd.sock --namespace bench78821163 --name dind --image bench78821163.local/dind:1 --data /var/lib/bench78821163/dind-data --ca /var/lib/bench78821163/pki/ca.crt

It creates the container dind from the image bench78821163.local/dind:1 (a Docker engine: its dockerd is the first process of the container) with oci.WithPrivileged, bind mounts for the data directory of the inner Docker and for the CA certificate of the private registry (under /etc/docker/certs.d/private-repo.local/), and starts it. The containerd is a private one with its own socket, /run/bench78821163/containerd.sock and the containerd namespace is bench78821163. The container dind is running now, made by this program. To run a command in it, for example: sudo ctr -a /run/bench78821163/containerd.sock -n bench78821163 tasks exec --exec-id e1 dind docker pull private-repo.local/app:seed

The problem: the Docker inside the container cannot pull from the private registry. The pull of private-repo.local/app:seed ends with: Get "https://private-repo.local/v2/": dial tcp: lookup private-repo.local on [::1]:53: ... (the lookup goes to the loopback on port 53, where nothing listens).

What the machine has for the container: a pod network, as a Kubernetes pod would get it from its CNI plugin. It is the network namespace /run/netns/bench78821163-pod, in which eth0 has the address 10.78.21.2/24 and is connected through a bridge to the node network 10.78.21.0/24. On the node network, 10.78.21.1 runs a DNS server (port 53) that knows the name private-repo.local, and the private registry itself (HTTPS, port 443, the certificate is signed by the CA that the container already gets). The network namespace of the host cannot reach 10.78.21.1, so a pull by ctr or by a Docker on the host is no way to the registry, and it does not count.

Your task is to change the Go program so that the container it creates can pull images from private-repo.local and run them with the Docker inside. The container has to be part of the pod network: it must run in the network namespace /run/netns/bench78821163-pod and must not use the network namespace of the host. The name private-repo.local has to be resolved through the DNS server 10.78.21.1 (no entries in a hosts file, no changed registry address, no insecure registry setting). A running container cannot change its namespaces, so the container that exists has to be removed and made again by the changed program.

The check removes the container dind, builds the sources in /tmp/bench78821163/app (so leave the program's source there, with its go.mod), runs the built program with exactly the command line above (no other flags, with sudo), and requires: the new container dind runs from the image bench78821163.local/dind:1 in the network namespace of the pod, not in the host's; the Docker inside answers; a new image, unknown to the Docker inside, is put into the registry, and the Docker inside pulls it by its name private-repo.local/app and the new tag and runs it with a nonce (docker run --network none IMAGE NONCE hold 60) and prints the nonce; the DNS server and the registry have seen the questions and the requests of that pull from the container's address.

Rules: the program keeps using the containerd Go client and keeps making the container privileged and from the image given by --image, with the inner Docker as its dockerd; do not change the containerd, its configuration, the DIND image, the registry, the DNS server or the networks of the machine; do not use docker, podman or nerdctl on the host, and use ctr only to look at the container and to remove it. Nothing may be downloaded except the Go modules. Your commands must finish by themselves: no interactive prompts, and no command that waits forever.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime commands need sudo.

Return the commands needed to complete the task (for example the commands that change main.go, build it, remove the old container and run the program).
