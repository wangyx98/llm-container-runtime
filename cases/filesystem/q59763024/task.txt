This machine runs a small container node of its own for this exercise: a containerd (the node's container runtime, with its CRI; socket /run/bench59763024/containerd.sock) and one
pod, the "ingress controller". There is no Kubernetes cluster. The machine's own container tools are not touched. Three wrappers (all call sudo themselves):

    /tmp/bench59763024/bin/node-crictl     # crictl of this containerd
    /tmp/bench59763024/bin/node-ctr        # ctr of this containerd; the images are in the namespace k8s.io: node-ctr -n k8s.io images ls
    /tmp/bench59763024/bin/node-apply      # apply the deployment: remove the controller pod and make it again from the two files below, start its container

(Adaptation: the question is about ingress-nginx 0.27.1 on CentOS 8 with containerd 1.2.0 that stops with "could not create PEM certificate file ... permission denied" and, after that,
"bind() to 0.0.0.0:80 failed (13: Permission denied)", with runAsUser 101 and drop ALL / add NET_BIND_SERVICE in the deployment. This exercise is a controller of its own with an image built
for it: it is not a reproduction of that incident, and the causes you find here are this lab's.)

The deployment is the pair of files /var/lib/bench59763024/deploy/pod.json (the pod: name ingress-nginx-controller, host network) and controller.json (the container: image
localhost/bench59763024/controller:1, command /entry.sh, run as 101:101, capabilities: drop ALL, add NET_BIND_SERVICE, privilege escalation allowed), in the format of crictl. The controller
stores its default certificate at /etc/ingress-controller/ssl/default-fake-certificate.pem at its start and then serves HTTP on port 80 (/healthz answers ok; /fake-certificate returns the
stored certificate). It has been applied once and has stopped.

    $ /tmp/bench59763024/bin/node-crictl ps -a
    $ sudo cat /run/bench59763024/logs/controller.log

Your task: make the controller run and answer on port 80 from the deployment files, as it is meant to: as uid 101 and not as root, with NET_BIND_SERVICE as the only capability it may ever
have, not privileged. Requirements:

1. After node-apply the pod ingress-nginx-controller is the only controller pod, its container controller is running the given image and command, and http://127.0.0.1:80/healthz answers ok
   and http://127.0.0.1:80/fake-certificate returns the certificate the controller stores (valid PEM). The listener on port 80 is the controller's own process. The fix is in the
   deployment files (and what they refer to): applying them again gives the same result.
2. The process runs as uid 101 and gid 101 (no root, not in the group 0), the capability bounding set of the container is NET_BIND_SERVICE and nothing else, the container and the pod are not
   privileged, and the program it runs is the image's own /bin/busybox (not another one). The files /entry.sh, /www and /ingress-template and the certificate are not replaced by mounts; mounts
   over /bin/busybox and /etc/ingress-controller[/ssl] are fine.
3. The images stay as given (not replaced; nothing inside containerd's store is edited by hand). The host's settings (sysctl, for example net.ipv4.ip_unprivileged_port_start) are not
   changed. The node's files and wrappers, and its containerd process, stay as they are. Nothing is downloaded or pulled.

Use sudo for the node's files if you need it. A command you start with a shell keeps the pipes of that shell open unless you redirect its output.
