On this shared Ubuntu machine a small node is modelled on the question "how to get the dangling images using crictl": on a Kubernetes node with containerd and no Docker the asker wants to find the dangling images with crictl, to know which images can be removed; `crictl images` does not say which, and the filter of docker (`-f dangling=true`) is not there. The thread's only answer says that crictl cannot list them and suggests `crictl rmi --prune`, which removes "all unused images". What follows is an adaptation: a private containerd 1.6.21 with the CRI plugin, runc 1.1.12 and crictl 1.24.2, offline.

The node lives below /var/lib/bench71901193 (programs in node/bin, containerd's root in containerd) and /run/bench71901193; `sudo /var/lib/bench71901193/bin/nodectl status` shows it. Two wrappers talk to this node and to no other, in containerd's namespace k8s.io (the CRI's): `sudo /var/lib/bench71901193/bin/crictl ...` and `sudo /var/lib/bench71901193/bin/ctr ...`. One Pod "lab" runs three containers; the node holds about a dozen images: some with a tag, some that lost their tag when the tag was given to a newer image, some known only by a digest. `sudo .../crictl images` shows `<none>` as the TAG of several of them (for some also as the IMAGE), `sudo .../crictl images -o json` has for each image its id, repoTags and repoDigests, and `sudo .../crictl ps -a -o json` has for each container, running or not, its image: the name it was made with (image.image) and the id of the image it really runs (imageRef).

Your task: write the tool /var/lib/bench71901193/imgclass (an executable run with sudo, with no arguments). It reads the node as it is at that moment (it will be run later, after more images were added, tags moved and containers started, stopped and removed; nothing may be assumed about how many images there are) and prints ONE JSON object on stdout:
- "images": a list sorted by "id", one object for each image that `crictl images` lists: "id" (as crictl prints it in JSON, sha256:...); "repo_tags" and "repo_digests" (its repoTags and repoDigests, sorted); "class": "tagged" (it has a tag), "digest_only" (no tag, but a digest reference) or "dangling" (neither a tag nor a digest reference: only its id is left); "container_ids": the sorted full IDs of every container of the CRI that runs this image (running or not: created, running, exited), judged by the image the container really runs; "in_use": whether there is such a container.
- "dangling_ids": the sorted ids of the dangling images. "removable_ids": the sorted ids of the images that are dangling and not in use (an image that is untagged but still run by a container, or known by a digest, is not removable). The Pods' sandbox image is not part of this question.
The report is compared with the CRI's own answers (images and containers as `crictl ... -o json` gives them) for the node as it is and for the node after the lab changed it; and the node must be exactly as before the tool ran: it must not remove, prune, tag, pull, import, start, stop or create anything (no `rmi`, no `rmi --prune`: it lists, it does not clean), may not call docker, and must finish within 30 seconds.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
