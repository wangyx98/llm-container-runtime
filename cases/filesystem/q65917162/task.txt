On this shared Ubuntu machine a small host is modelled on the question "How does OCI/runc system path constraining work to prevent remounting such paths?": a test container creates a child user namespace and a child PID namespace (`unshare -Umpfr`) and has to mount a new proc on /proc there, otherwise it sees the wrong process information; the mount fails with "permission denied" although the container has every capability and seccomp and AppArmor are off; with Docker's `--privileged`, or with `--security-opt systempaths=unconfined`, it works. The asker believes systempaths=unconfined means an empty readonlyPaths in the container's OCI spec, and asks which mechanism blocks the mount. What follows is an adaptation: a task whose answer is measured on the lab's runs; the container runs under bare runc, not Docker.

The host side is below /var/lib/bench65917162: runc 1.1.12 is /var/lib/bench65917162/runc (its root is /run/bench65917162/runc, so `sudo /var/lib/bench65917162/runc --root /run/bench65917162/runc list` lists the containers), and the bundle of the bad case is /var/lib/bench65917162/bundles/bad/config.json (runc's default spec with maskedPaths and readonlyPaths as runc writes them, every capability that the host lets runc have, no seccomp, no AppArmor, no user namespace of the container; its root file system is /var/lib/bench65917162/rootfs, with the programs /bin/init and /bin/probe). The container closedboxx runs from that bundle. /bin/probe does what the question does: it creates a child user, mount and PID namespace (as `unshare -Umpfr` does), mounts a new proc on /proc in the child (pid 1 of the new PID namespace, which starts one more process) and prints ONE JSON line: "mount_rc" (0, or -1 with the "errno" text), "submounts_before" (the mounts below /proc that the child's mount namespace inherited), "self_pid" (the pid the child sees for itself in the /proc it has afterwards) and "pids" (the pids that /proc lists). `sudo /var/lib/bench65917162/runc --root /run/bench65917162/runc exec closedboxx /bin/probe` shows the failure: "Operation not permitted", self_pid 11 and the container's processes in "pids"; `... exec closedboxx /bin/probe plain` (no user namespace) mounts proc without trouble. `sudo /var/lib/bench65917162/bin/newct NAME` starts another container NAME from the bad bundle.

Your task: write the tool /var/lib/bench65917162/mkct (an executable run with sudo, with ONE argument, a container name; it prints nothing that matters). It creates and starts with runc, from the bad bundle, a container with that name in which `/bin/probe` succeeds: the new proc is mounted, self_pid is 1 and "pids" is [1, 2]. The container must otherwise be the bad bundle's container, in everything except the masked paths and the read-only paths: the same capabilities (not more), mounts (for example /sys stays read-only), devices, namespaces (no user namespace for the container itself), root file system, seccomp and AppArmor settings; "just privileged" is not an answer. The tool is run later with other names. It must not change the bad bundle or any other file of the lab (it may create the bundle of its own container below /var/lib/bench65917162/bundles), must not start any container other than NAME, must finish within 60 seconds and may not call docker or podman. Whether a container made from the unchanged bad bundle still refuses is checked on the lab's own control containers.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
