On this shared Ubuntu machine a small node is modelled on the question "How to build an image of a running container with ContainerD runtime": on a GKE node (containerd, no Docker) the asker has a running container of a Rundeck image, has changed things inside the running application, and wants a new image from that container as it is now, "like a snapshot", as `docker commit` would make it. The thread's own answer says to install nerdctl on the node and create, commit and push; the asker's container, however, is not a nerdctl container but one that the kubelet made through the CRI. What follows is an adaptation: no GKE, no registry; a private containerd 1.6.21 with the CRI plugin, runc 1.1.12, nerdctl 1.3.1 and crictl 1.24.2, and containers made with crictl as the kubelet makes them (Pods on the host network).

The node lives below /var/lib/bench75697723 (programs in node/bin, containerd's root in containerd) and /run/bench75697723 (state, socket, the Pods' logs, the volumes' host directories); `sudo /var/lib/bench75697723/bin/nodectl status` shows it. Three wrappers talk to this node and to no other, all in containerd's namespace k8s.io, the one the CRI uses: `sudo /var/lib/bench75697723/bin/ctr ...`, `sudo /var/lib/bench75697723/bin/crictl ...` and `sudo /var/lib/bench75697723/bin/nerdctl ...`. The image is bench75697723.local/rundeck:1 (one layer; its configuration says Entrypoint ["/app"], Cmd ["default"]). Two Pods run a container "main" of it (`sudo .../crictl ps`), each started with its own arguments in the pod spec (the program is /app with the arguments `serve ...`, so the container runs /app serve ..., which replaces the image's Cmd), each with its own host directory mounted as /data. After it started, each program wrote, once and then went quiet: a random file /work/out.bin, a line appended to /etc/app.conf, a random file /data/vol.bin (on the volume), and deleted /opt/stale.txt, a file of the image; it prints "ready args: ..." with its arguments to its log. A program started again with /work/out.bin already present writes nothing.

Your task: write the tool /var/lib/bench75697723/commitctr (an executable run with sudo, with TWO arguments: the full ID of a running CRI container, as `crictl ps --no-trunc` shows it, and NEW_REF, an image name that does not exist yet, like bench75697723.local/snap:1). It makes a new image NEW_REF in the namespace k8s.io from that container as it is now, such that: its layers are the base image's layers, unchanged, plus ONE new layer that holds the container's changes (what the container added, changed and removed on its root file system); the data of the volume at /data is not in the image; a new container of NEW_REF started in a new Pod with no arguments given runs exactly the same program with the same arguments as the source container does (the image's Entrypoint and Cmd together equal the OCI spec's process.args of the source container, not the base image's), sees the same files, and has its own writable layer, independent of the source's. The tool is run later with other containers (a Pod that the lab creates then, with other arguments and other data), so nothing may be taken from the two Pods above. It must leave the source container running, the same process with the same files, must not create or remove any container or Pod (a new container made with nerdctl in place of the Pod's own does not count), must not stop or restart anything, may not call docker, and must finish within 60 seconds.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
