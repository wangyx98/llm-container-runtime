On this shared Ubuntu machine a small host is modelled on the question "joined process cannot write ns_last_pid of the container": a process of the host joins the namespaces of a runc container and tries to write /proc/sys/kernel/ns_last_pid (the number after which the next process of a PID namespace gets its pid; CRIU and similar tools set it to give a process a chosen pid), and gets "Read-only file system"; the same write works for the host's own file. The thread has no explanation: a comment asks what kind of container it is (runc), and the only answer says to run the container with --privileged. What follows is an adaptation: a task whose answer is measured on the lab's runs.

The lab is two containers made by bare runc 1.1.12 from runc's default spec (own PID, mount, network, IPC and UTS namespaces; runc's default read-only paths, which include /proc/sys; no user namespace; no --privileged). The host side is below /var/lib/bench63752123: runc is /var/lib/bench63752123/runc (its root is /run/bench63752123/runc, so `sudo /var/lib/bench63752123/runc --root /run/bench63752123/runc list` lists the containers and `... state NAME` gives the pid of a container's init), the ids of the two containers are in /var/lib/bench63752123/etc/target.id and other.id, and `sudo /var/lib/bench63752123/bin/newct` makes another running container like them (it prints its id). The containers' root file system has only one static program with the commands init, wr, cat, ls and id (no shell). The asker's attempt reproduces here: `sudo nsenter -t <init pid of target> -m -p /bin/wr /proc/sys/kernel/ns_last_pid 5000` prints "Read-only file system". The host's own file, /proc/sys/kernel/ns_last_pid, is writable for root. (Writing the file needs CAP_SYS_ADMIN, or CAP_CHECKPOINT_RESTORE on kernels from 5.9, in the user namespace that owns the PID namespace; here that is the host's, and root has it.)

Your task: write the tool /var/lib/bench63752123/nsfork (an executable run with sudo, with TWO arguments: the id of a running container of the lab and an integer VALUE between 2000 and 30000; its stdout is ONE JSON object). It writes VALUE into the ns_last_pid of the PID namespace of THAT container, then starts one new process (a child) that lives in that PID namespace, so that its pid there is VALUE+1, and the child stays alive for at least 2 seconds after the tool returns (for example it is a `sleep 3`; it ends by itself, nothing may stay in the container afterwards). The JSON object has the fields:
- "container": the id it was given;
- "value": VALUE as an integer;
- "child_ns_pid": the pid of the child in the container's PID namespace (VALUE+1);
- "child_host_pid": the pid of the same child on the host (the host sees every process of the containers).
The tool is run later for other containers that did not exist when it was written, with other values, and what it prints must be right for them. It must really write the container's ns_last_pid (a write to some other file does not count), must not write the host's own ns_last_pid, must not start, stop or delete a container, and must not change the containers' configuration or mounts (/proc/sys stays read-only inside the containers). It must finish within 60 seconds, may not call docker or podman, and must not change the lab's files.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
