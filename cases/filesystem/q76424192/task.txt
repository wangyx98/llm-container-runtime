On this shared Ubuntu machine a small node is modelled on the question "Kubernetes all images are duplicated with same id": on a k3s node with an external containerd (1.6.21, nerdctl 1.3.1, BuildKit 0.11.6) every image appears twice in the listing, with the same ID and size, one of the two untagged, for the images the cluster pulls and for the images built with nerdctl; `crictl rmi --prune` does not remove the untagged ones, and the asker fears that the disk holds every image twice. What follows is an adaptation: no k3s (the kubelet's pulls are CRI PullImage calls, made here with crictl) but the same containerd, nerdctl and BuildKit versions.

The node lives below /var/lib/bench76424192 (programs in node/bin, containerd's root in containerd, BuildKit's root in buildkit, the registry's storage in registry) and /run/bench76424192; `sudo /var/lib/bench76424192/bin/nodectl status` shows its three daemons (containerd with the CRI plugin, a registry on 127.0.0.1:35424, buildkitd). Three wrappers talk to this node and to no other: `sudo /var/lib/bench76424192/bin/ctr -n k8s.io ...` (the namespace the CRI and nerdctl use), `sudo /var/lib/bench76424192/bin/crictl ...` and `sudo /var/lib/bench76424192/bin/nerdctl ...` (nerdctl with its BuildKit). Two images were pulled with `crictl pull` from the registry (app/a:1, app/b:1) and one was built with `nerdctl build` (built/one:v1); the registry also holds app/c (tags 1 and latest) and app/d. `nerdctl images` shows eight lines with three different IDs, `crictl images` three images; containerd's content store is /var/lib/bench76424192/containerd/io.containerd.content.v1.content (blobs below blobs/sha256) and its snapshotter's directory /var/lib/bench76424192/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots.

Your task: write the tool /var/lib/bench76424192/imgreport (an executable run with sudo, with no arguments). It reads the node as it is at that moment (it will be run later, after more pulls and builds, and the numbers must follow; nothing may be assumed about how many images there are or how big they are) and prints ONE JSON object on stdout, answering whether the extra lines are extra storage:

- "records_total": the number of image records of the namespace k8s.io (what `ctr -n k8s.io images ls` lists), "groups_total": the number of different targets (manifest or index digests) those records point to, "alias_records": records_total minus groups_total.
- "groups": a list, sorted by "target_digest", one object per target: "target_digest"; "image_id" (the digest of the image's config); "records": a list sorted by name of {"name", "kind"}, kind being "image-id" for a name that starts with "sha256:", "repo-digest" for a name that contains "@sha256:", otherwise "tag"; "blob_digests": the sorted digests the target needs in the content store (the target itself, its config, its layers; for an index the manifests of it that the store has, each with its config and layers); "content_bytes": the bytes of those blobs, each once.
- "listed_bytes": the sum, over all records, of their group's content_bytes (what adding up the lines of a listing suggests).
- "content_store_bytes": the bytes of containerd's content store directory above; "snapshots_bytes": the bytes of the snapshotter's directory above.
- "freed_by_removing_alias_records_bytes": the bytes of blobs that no record would reach any more if, in every group, all records but one were removed; "unreferenced_content_bytes": the bytes of blobs in the content store that no record's target reaches (in the sense of blob_digests).
- "shared_layers": the layers (digest, "bytes" of the blob, "groups": the sorted target digests) that more than one group uses, sorted by digest, and "shared_layers_saved_bytes": the sum of bytes times (number of groups minus one).
- "buildkit": {"root": "/var/lib/bench76424192/buildkit", "bytes": the bytes of that directory, "blobs_also_in_containerd": the sorted digests ("sha256:...") of the blobs of BuildKit's own content store (content/blobs/sha256 below the worker directory in its root) that containerd's content store has too, "shared_blob_bytes": the bytes of those blobs as containerd's store holds them}.

"Bytes" are allocated bytes, 512 times st_blocks as stat or `du -B1` give them (not the sizes of the files); for a directory: everything below it and the directory itself, every inode (st_dev, st_ino) counted once. The numbers are compared with the lab's own measurements: within 1% (and 64 KiB), the groups' content_bytes and the shared layers' bytes within 1% and 16 KiB, buildkit.bytes within 5% and 512 KiB, everything else that is a count, a name or a digest exactly (freed_by_removing_alias_records_bytes must be exactly what the definition gives). The tool must not change anything on the node (no removing or tagging of images, no prune, no pull, no build, no restart; the lab compares the image records, the blobs, the snapshots, the CRI's image list and BuildKit's blobs before and after), may not call docker, and must finish within 60 seconds. The node's daemons must keep running.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
