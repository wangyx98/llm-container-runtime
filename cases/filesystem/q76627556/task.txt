On this shared Ubuntu machine a small node is modelled on the question "containerd apparently storing multiple copies of the same container - how to test it's not a wasteful duplication?": on a MicroK8s node the asker runs ten pods of one image, and `du` of the directory of each container below containerd's state (the rootfs of the container) shows the whole image size, ten times; the disk is not ten times as full, and the asker wants to know how to prove that the layers are stored once, and how to see what the containers really cost. Counting images with crictl does not prove it: the answer has to come from the mounts, the shared lower directories, the upper directories and the blocks that are really allocated. What follows is an adaptation: a private containerd 1.7.20 (no Kubernetes, no CRI plugin) with the overlayfs snapshotter, and a tool to write.

The node lives below /var/lib/bench76627556: containerd's root is /var/lib/bench76627556/containerd (the snapshotter's directory is /var/lib/bench76627556/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots) and its state is /run/bench76627556/containerd. `sudo /var/lib/bench76627556/bin/ctr -n k8s.io containers ls` lists the containers (namespace k8s.io, as Kubernetes uses); `ctr` here talks to the node's containerd, not to any other. There is one image, bench76627556.local/ml-scraper:latest: a big layer of random, incompressible data (the file /big.bin, some tens of MiB) and a small one with the program the containers run. Ten containers of it are running and none has written anything. The root file system of a container ID is an overlay mount at /run/bench76627556/containerd/io.containerd.runtime.v2.task/k8s.io/ID/rootfs; `sudo du -sh` of such a directory shows the whole image, for every container. `sudo /var/lib/bench76627556/bin/mkset N [COPYUP [WRITERS [MODIFIED]]]` starts N more containers of the image: COPYUP of them open /big.bin for writing, which makes overlayfs copy the whole file into the container's upper directory unchanged, WRITERS write a new file of a few MiB, MODIFIED append 1 MiB to /big.bin (copy-up, then change).

Your task: write the tool /var/lib/bench76627556/dupreport (an executable run with sudo, with no arguments). It reads the node as it is at that moment (it will be run later, when there are more containers, some of them with copied-up files, and the numbers must follow; nothing may be assumed about how many containers there are or how big the image is) and prints ONE JSON object on stdout:

- "containers": a list, sorted by "id", with one object for every container of the namespace k8s.io that has a root file system mounted: "id", "rootfs" (the mount point), "upperdir" (the overlay's upper directory, as the mount has it), "upper_bytes" (the bytes in that upper directory, the directory itself included) and "copied_up_bytes" (the bytes of the regular files in the upper directory that a lower directory has at the same path with the same size and the same content: files copied up and not changed).
- "shared_lower": {"dirs": the overlay's lowerdir list as the mounts have it, topmost first (all containers of the lab have the same list), "bytes": the bytes of those directories together}.
- "naive_du_bytes": the sum, over the containers, of what `du -s -B1` prints for their "rootfs"; "physical_bytes": the bytes of the snapshotter's directory (the snapshots directory above); "double_counted_bytes": naive_du_bytes minus physical_bytes; "copied_up_bytes_total": the sum of the containers' "copied_up_bytes".

"Bytes" are allocated bytes, 512 times st_blocks as stat or `du -B1` give them (not the sizes of the files), with every inode (st_dev, st_ino) counted once in one measurement. The numbers are compared with the lab's own measurements: within 1% (and 64 KiB), "upper_bytes" within 1% and 32 KiB, "shared_lower.bytes" within 1% and 16 KiB, "copied_up_bytes" within 8 KiB. All values are integers. The tool must not change anything on the node (no deleting, pruning, mounting, starting or stopping; the lab compares the files of the snapshotter, the mounts, the containers and their tasks before and after), may not call docker or crictl, and must finish within 60 seconds. The lab's later containers are made by its own checks; the containers of the lab must still be running.

The current user has passwordless sudo. Unless stated otherwise, assume container-runtime and system commands need sudo.

Return the commands needed to complete the task.
