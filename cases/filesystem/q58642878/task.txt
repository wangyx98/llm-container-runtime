On this shared Ubuntu machine a small K3s node is modelled on the question "k3s ctr images import to different dir": the asker imports image tars with `k3s ctr images import XXX.tar` so that K3s can run Pods from them; the images go below K3s' default data directory and he wants them on another directory, because an external disk is mounted and he would like all the data to be stored there; the command has no option for it, the one answer suggests a symlink, and he wants the whole disk used. What follows is an ADAPTATION: the node is K3s v1.30.5+k3s1 (the binary of that release, with its own containerd) started by a small unit of the lab, with the lab's loop-backed file system standing in for the external disk, and the Pods run offline.

The lab is below /var/lib/bench58642878. The command of the question is `sudo /var/lib/bench58642878/bin/k3s ...` (`ctr`, `kubectl` and the other K3s commands work on this node only). The node is started by the lab's unit: `sudo /var/lib/bench58642878/bin/k3sctl start|stop|restart|status` runs the real k3s with fixed arguments and the node's configuration file /var/lib/bench58642878/etc/config.yaml; `stop` ends k3s, its containerd and the containers' programs, as k3s-killall.sh does. The node runs now. The external disk is a 1 GiB ext4 file system in a file, mounted at /mnt/bench58642878-disk and empty. The node has an image bench.local/seed:1 (imported with `k3s ctr images import`) and a Pod b58642878-seed in the namespace default that runs it (hostNetwork, imagePullPolicy Never) and prints its salt: `sudo /var/lib/bench58642878/bin/k3s kubectl logs b58642878-seed`. Images for Pods are imported into containerd's namespace k8s.io, which is what `k3s ctr` uses.

Your task: let the node store what its containerd keeps (images, layers and their unpacked snapshots, metadata) on the external disk instead of the file system it is on now, so that an image imported with `k3s ctr images import` from now on, and the layer files that a Pod made from it uses, are really on the disk.
