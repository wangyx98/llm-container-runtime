Regardless of whether Docker, containerd, or CRI-O started it, is there a
way to tell -- at the bare runc layer -- whether a runc container is
running "privileged"?

The honest answer is: runc itself has NO notion of "privileged" at all.
`runc spec`'s config.json, and the internal state.json that runc writes
under its --root directory for every container it creates, never contain
a field called "privileged" anywhere. That word is purely an abstraction
invented by higher-level tools (Docker's --privileged flag); it does not
exist at the runc/OCI-runtime level. So `grep -ri privileged` against
config.json or state.json will find nothing, and hardcoding "yes" or "no"
regardless of the container is exactly the kind of trick this task is
designed to catch.

What DOES exist at the runc level -- and what Docker's --privileged flag
actually configures under the hood -- is a specific combination of real,
inspectable primitives:

  1. The Linux capability set granted to the container's process
     (state.json's config.capabilities.Bounding list). A normal
     container gets a small handful (bare `runc spec`'s own default is
     just 3: CAP_AUDIT_WRITE, CAP_KILL, CAP_NET_BIND_SERVICE). A
     privileged one gets (near-)ALL of them.
  2. The cgroup device access rules (state.json's config.cgroups.devices
     list). A normal container has an explicit DENY-all wildcard rule
     ({"type": 97, "major": -1, "minor": -1, "allow": false}) plus a
     short allowlist of specific device nodes. A privileged container
     instead has an ALLOW-all wildcard rule ({"type": 97, "major": -1,
     "minor": -1, "allow": true, "permissions": "rwm"}) -- type 97 is
     the ASCII code for 'a' (all device types).
  3. no_new_privileges (state.json's config.no_new_privileges). This is
     "on" by default (bare `runc spec` sets it true). Because Go's JSON
     encoder omits `false`-valued fields with `omitempty`, when this
     protection is turned OFF the key is entirely ABSENT from
     state.json rather than present with value false -- so "key present
     and true" means the protection is ON, and "key absent" (or
     present-and-false) means it's OFF.
  4. The /proc and /sys lockdown paths -- config.mask_paths and
     config.readonly_paths. By default these list several sensitive
     paths (/proc/kcore, /proc/acpi, /proc/sys, etc.). A privileged
     container has both lists cleared to empty.

A container only counts as the practical equivalent of
`docker run --privileged` if ALL FOUR of these hold together. Any ONE of
them alone is NOT sufficient proof -- for example, a container can
legitimately be handed extra Linux capabilities (say, CAP_NET_ADMIN and
CAP_SYS_PTRACE for a debugging/networking tool) without also getting
open device access or dropped /proc,/sys hardening, and vice versa. Real
production containers do this all the time; treating "has some elevated
capabilities" or "has open device access" alone as proof of
"--privileged-equivalent" produces false positives.
