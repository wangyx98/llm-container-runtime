The node is called bench75817724-node. k3s reads its options from /etc/rancher/k3s/config.yaml and is started and stopped with a script, /var/lib/bench75817724/bin/k3sctl (start, stop, restart, status; run it with sudo). The k3s binary is /var/lib/bench75817724/bin/k3s; the embedded containerd writes its configuration below /var/lib/rancher/k3s/agent/etc/containerd. To talk to the embedded containerd through the CRI (the interface the kubelet uses to pull images and start Pods):

    sudo /var/lib/bench75817724/bin/k3s crictl pull ...

The team keeps its images in a private registry, registry.bench75817724.test:5000, over HTTPS with a certificate that was signed by the company's own CA (self-signed, not a public CA). The certificate of that CA is the file /var/lib/bench75817724/pki/ca.crt. The only way out of this machine is the company egress proxy, which k3s and its containerd already use and which resolves that registry name; nothing else is reachable.

Docker clients accepted the certificate once the CA file was copied to /etc/docker/certs.d/registry.bench75817724.test:5000/. The engineer then copied the same ca.crt file to /etc/containerd/certs.d/registry.bench75817724.test:5000/ca.crt and added config_path = "/etc/containerd/certs.d" to the registry section of containerd's config.toml below /var/lib/rancher/k3s/agent/etc/containerd, but a Pod that uses the image registry.bench75817724.test:5000/hello-web:latest still cannot pull it. Requirements:
