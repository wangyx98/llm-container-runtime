## Why it was not collected
- The warning is a consequence: the shim process is gone and containerd cleans up. A kernel OOM kill of the shim, an external kill and a crash of the shim (a Go 1.10 runtime fault is the answer's guess) all produce it; the thread has nothing that separates them, and the asker's "memory is fine" is not evidence about the shim's cgroup.
- The string is not reproduced by a current stack. Measured on 2026-11-20 with containerd 2.4.2 (private node, `kill -9` of a pod's `containerd-shim-runc-v2`): `shim disconnected`, `cleaning up after shim disconnected`, `cleaning up dead shim` (all info), `failed to get task exit status ... ttrpc: closed`, `failed to delete task: ttrpc: closed` (error); no `killed shim` warning. The VM's containerd 2.2.1 uses the same new wording, so a `kill -9` on the VM does not even reproduce the thread's lines, and would not be the original incident anyway.
- The original stack (Docker 18.09, kernel 4.4, Go 1.10) cannot be run on the VM (Docker 27, cgroup v2, kernel 5.15) and the failure appears after days, with no trigger.
- Coverage: q63457756 (shim crashes at start because of the build flags) and q64401699 (CRI recovery) already cover shim death as a failure; the new element would only be attributing a shim death after the fact.
