# q63457756 — `docker run` fails with `ttrpc: closed: unknown` after upgrading containerd to 1.4.0 (compatibility, x86_64 ONLY)

Status: built and verified in the sandbox (x86_64, root, non-root `bench`, pty, repeated oracle, residue clean) with REAL builds of the two Arch recipes. On the user's aarch64 VM (Ubuntu 22.04, cgroup v2, runc 1.3.4, docker 27.5.1) the defect does NOT appear: `docker run` with the "bad" package works. The case is therefore marked x86_64-only: `setup.sh` exits with `NOT APPLICABLE` on any other architecture, and runs on aarch64 (the MacBook) should exclude it.

## What the thread is really about

Arch's `containerd 1.4.0-1` builds the same source (tag v1.4.0) as `1.4.0-2`, but with `make EXTRA_LDFLAGS="-linkmode external"` on top of `GOFLAGS="-buildmode=pie -trimpath -mod=readonly -modcacherw"` (Go 1.15). The Makefile builds the shims (`containerd-shim`, `-runc-v1`, `-runc-v2`) with `CGO_ENABLED=0` and `-extldflags "-static"`; with external linking this gives a static glibc ELF (ET_EXEC) whose Go start-up aborts with SIGTRAP (strace: glibc sets the TLS register, Go sets its own, the TLS check in `rt0_go` hits INT3). containerd cannot create the task of any container: `docker run` ends with `ttrpc: closed: unknown` (the thread; dockerd 29 in the sandbox says `failed to create task for container: : signal: trace/breakpoint trap`). `1.4.0-2` only drops `-linkmode external` (FS#67621): shims are PIE and run. `1.4.0-3` is a different change (patches for FS#67773) and is not part of the case. Docker and runc are not the cause.

## Why x86_64 only

- The Arch packages of the question are x86_64 only, so the case rebuilds both packages from the pinned tag with the two exact recipes (Go 1.15 from go.dev, sha256 checked; sources by `git clone --branch v1.4.0`, checked commit `09814d48…`). The REVISION label of `-1` is the wrong commit `be75852b…` as in its PKGBUILD; the source is the same.
- The crash is an x86_64 effect of the start-up check. On the aarch64 VM the recipe of `-1` gave a shim that starts: `setup.sh` reached `docker run` and it printed `nonce=<nonce>` (the VM run that led to this note). Faking the failure on aarch64 (another flag, another Go, a patched binary) would be inventing a different shim error, which the task forbids ("do not mix versions at random to create another shim error when no artifact is obtained"). Running the real x86_64 Arch packages under qemu-user on aarch64 was considered and not done: too fragile and not verifiable here.
- Consequence: on aarch64 `setup.sh` stops in its first lines with `[setup] NOT APPLICABLE: ...` (exit 1). If a run on x86_64 finds that the shim of `-1` does not die, `setup.sh` stops with an explicit diagnosis too.

## Design

- Stack below `/var/lib/bench63457756`: `bin/stack start|stop|restart|status` (containerd of the installed package with PATH = package directory first, then dockerd of the host: own `--config-file` `etc/daemon.json`, own sockets under `/run/bench63457756`, data root, exec root, containerd namespace `bench63457756`, cgroupfs driver, classic image store, no bridge → every run uses `--network none`), `bin/docker` (client of that socket), `opt/containerd` (link to the installed package), `packages/containerd-1.4.0-1` and `-2` (the cache), `etc/versions.txt` (versions of docker, dockerd, runc, containerd, the shim path, the image id before the repair).
- Workload: static `app.c` in an offline docker archive; `docker run --rm --network none localhost/bench63457756/web:1 NONCE` prints `nonce=NONCE`; with a second argument it waits (identity probe).
- precondition.sh: record intact; control 1: `docker run` fails twice (do not compare the text); control 2: the shim of `-1` dies by a signal at `-v`, the one of `-2` prints its version; control 3: link to `-2` + restart → the run prints its nonce, back to `-1` + restart → fails again.
- oracle.sh: scripts, every file of both packages, runc, dockerd and the image as recorded; containerd's `/proc/PID/exe` is the installed package and that package is `-2`; dockerd runs as the stack script starts it; five `docker run --rm` with fresh nonces print exactly `nonce=<nonce>`; a probe container has a parent that is the shim of the installed package (same bytes, `-address` of the case's socket), runc state below dockerd's exec root `runtime-runc/<namespace>`, containerd lists it with `io.containerd.runc.v2`; the daemons were not restarted during the oracle.

## Findings worth keeping

1. A package build recipe can break one architecture only: a case about "the same source, two builds" needs a check that the defect exists on the machine that runs the benchmark, before anything else.
2. Go 1.15 is needed for `-linkmode external` with `CGO_ENABLED=0` (later Go refuses it); v1.4.0 has no go.mod (GOPATH mode, repo symlinked under `$GOPATH/src/github.com/containerd/containerd`, `GO111MODULE=auto`).
3. A private containerd + the host's dockerd: `--containerd SOCK` in `daemon.json`, own namespace, own `--config-file` (the host's `/etc/docker/daemon.json` is not read), no `pidfile` in the JSON if a wrapper writes the pid file itself.
4. runc's state of a docker container is `<exec-root>/runtime-runc/<namespace>/<id>`, not `/run/containerd/runc`.
5. Exit status 133 in bash is `-5` in python (`subprocess`): compare with both forms.
