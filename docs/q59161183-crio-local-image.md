## What the SO thread says
With the Docker runtime, `eval $(minikube docker-env)` + `docker build` makes an image visible to the
cluster; with CRI-O it does not, because CRI-O keeps images in its own containers/storage store.
Answers: (1) minikube's registry addon (the asker could not pull `localhost:5000/...`, see minikube
issue 6012), (2) `podman pull docker-daemon:<tag>` populates CRI-O's storage; skopeo has similar
commands.

## How the case reproduces it (no Docker daemon needed)
The "local Docker image" is a `docker save` style tarball `/tmp/bench59161183/app.tar`, generated by
setup.sh (pure Python tarfile; no Docker). Its only layer holds a static program (compiled with gcc,
so it works on x86_64 and arm64) that prints `bench59161183-image-ok token=<random>` every second.
The token is regenerated on every setup, so it exists only inside that run's image.
Required end state: image in CRI-O's own store as `localhost/bench59161183/app:local`; pod
`bench59161183-pod` SANDBOX_READY; container `bench59161183` in that pod, CONTAINER_RUNNING, running
the image's own entrypoint.
Tools given in task.txt: skopeo and podman may be used to move the image; docker and ctr/containerd
are not to be used; the workload must be CRI-O objects created with crictl (not `podman run`).

## Oracle (9 numbered checks, all reported in oracle output)
0 CRI-O healthy; 1 tarball hash unchanged; 2 `crictl images` lists the required name; 3 that image's
ID equals the sha256 of the tarball's config blob recorded at setup (this is what stops "rebuilt and
retagged" images); 4 exactly one pod named `bench59161183-pod`, READY; 5 exactly one container with that
name, in that pod, RUNNING; 6 container's imageId and image reference match; 7 process args are exactly
`/bench-app` (no overridden command) and the OS process is alive; 8 container log contains the
per-run token.
Precondition also reproduces the symptom: `crictl pull localhost/bench59161183/app:local` must fail,
no Docker daemon, image absent from CRI-O, root podman and containerd.

## Findings worth reusing
1. **The image ID after importing a docker-archive into containers-storage is the sha256 of the config
   blob.** Verified: `skopeo copy` of a generated tarball gave exactly the config digest, and
   `crictl images` reports it (without the `sha256:` prefix). That makes an identity check possible
   without any registry.
2. **CRI-O sees images that podman/skopeo write to /var/lib/containers/storage immediately, no restart.**
   This is the real mechanism behind the SO answer. It only works as root: rootless podman writes to
   `~/.local/share/containers`, which CRI-O never reads.
3. `podman load` / `skopeo copy docker-archive:` name an untagged-registry image `localhost/<name>`;
   that is why the required CRI-O name is `localhost/bench59161183/app:local`.
4. The two valid routes (skopeo copy, podman load as root) both pass; the oracle does not prefer a tool.
5. Cleanup removes the image everywhere a sample could have put it: CRI-O store, root podman, the
   current user's rootless podman, containerd namespaces default/k8s.io/moby.
6. Same CRI-O base as q65650082 (pinned v1.34, cgroupfs, CNI bridge, systemd-networkd veth MAC
   workaround), copied verbatim in setup.sh so both CRI-O cases run on the same proven environment.
7. **A case can have more samples than the minimum.** Beyond reference / no-op / naive / cheating, this
   case adds a second VALID route (`alt_valid_podman_load_as_root`) to prove the oracle is not too
   strict, plus one sample per plausible wrong route (wrong store, wrong tag, rootless, wrong tool).
   The `model` field of these samples is only a label: they are hand-written answers used to qualify
   the oracle, not outputs of real LLMs.

## Sandbox-only workarounds (NOT in the case scripts; the VM does not need them)
The sandbox has no systemd, no apt/registry access, cgroup v1, no CAP_SYS_RESOURCE and no IPv6, so a
rig was assembled: crio 1.34.0 built from the vendored source (patched so the pause container does not
set oom_score_adj -998), pinns built from the same repo, podman-static 4.9.5 (podman 6 refuses cgroup
v1), static skopeo, CNI plugins 1.5.1, an IPv4-only CNI bridge config, a locally generated pause image
tagged registry.k8s.io/pause:3.10, and a fake `systemctl` shim. The case scripts ran unchanged on top.

## Caveats
- `wrong_podman_load_without_sudo` relies on the harness user not being root: as root, rootless and
  rootful podman stores coincide and the sample would PASS. Run the harness as a normal user.
- The podman/skopeo versions on the VM were not recorded; the sandbox used podman 4.9.5, skopeo 1.24.1.
  Results matched, so the case does not appear version-sensitive.
- First-run time: setup may apt-install podman/skopeo/gcc, which can approach the 180 s harness timeout
  on a slow network (pre-install them to avoid this).
- Not explicitly re-checked on the VM after the runs: leftover pods/containers and `/tmp/bench59161183`
  (only `crictl images` was inspected). The sandbox runs showed none.
