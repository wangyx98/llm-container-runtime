# q59763024 — ingress-nginx 0.27.1: "unexpected error storing fake SSL Cert: could not create PEM certificate file ... permission denied", then bind() to 0.0.0.0:80 EACCES (CentOS 8, containerd 1.2.0) (filesystem) — DEFERRED

## What the thread is about
Helm chart `nginx-ingress` (controller `quay.io/kubernetes-ingress-controller/nginx-ingress-controller:0.27.1`) on CentOS 8, Kubernetes 1.17, containerd 1.2.0; the same chart worked on CentOS 7 with Docker. The controller exits with `F ssl.go:389 unexpected error storing fake SSL Cert: could not create PEM certificate file /etc/ingress-controller/ssl/default-fake-certificate.pem: ... permission denied`. Removing the `securityContext.capabilities` block (`drop: [ALL]`, `add: [NET_BIND_SERVICE]`) makes the pod start. The question was edited at 16:04 (after the answer and a comment) to add the deployment (`runAsUser: 101`, `allowPrivilegeEscalation: true`, drop ALL + add NET_BIND_SERVICE) and a SECOND error taken at 16:02: `nginx: [emerg] bind() to 0.0.0.0:80 failed (13: Permission denied)`.
Answer (one, +10): the new release's deployment uses `runAsUser: 101` (www-data -> 101 in the new image); an old deployment with another uid fails; set 101. A comment confirms it for 0.25.1 with uid 33 -> 0.27.1 with 101. The asker's reply: "yes, i am using 0.27.1, changing to 101 is not working".

## What is and is not explained
- Symptom 1 (cert dir write) is explained by the answer only for deployments whose runAsUser differs from the image's user (files/dirs under /etc/ingress-controller owned by uid 101 in 0.27.x). The question's own deployment already has 101, so the answer does not cover the asker's final state, and the thread never shows whether symptom 1 persists with 101.
- Symptom 2 (bind to port 80 with 101 and the caps block) is not answered. Candidates (none confirmed in the thread): the image's binaries carry the file capability `cap_net_bind_service=+ep` (set at image build) and that capability was lost when the old containerd/CentOS 8 unpacked the layers, or the capability sets that the runtime gives the process differ from what the file capability needs. This is a hypothesis; it was not verified against the real image.
- Conclusion for a case: two different permission failures on two paths (a file ownership one and a capability one); only the first has any stated fix, and that fix contradicts the asker's final deployment. A task that says "make the controller Ready" cannot name a single verified fix from the thread.

## Measured here (sandbox x86_64, kernel 6.18, cgroup v1; runc 1.1.12, static test program, no Kubernetes)
Process uid 101/gid 101, capabilities bounding/effective/inheritable/permitted = [NET_BIND_SERVICE], no ambient, `noNewPrivileges` false: opening a new file in a directory owned by 101 works; bind to port 80 gives `Permission denied` when the binary has no file capability and succeeds after `setcap cap_net_bind_service=+ep`; the same with `noNewPrivileges` true also succeeds (the bounding set contains the capability). So on a modern runtime "uid 101 + drop ALL + add NET_BIND_SERVICE" works exactly when the binary still has its file capability; the symptom of the thread is reproduced by a binary WITHOUT it. (Not measured: a directory owned by another uid; the file-capability loss on unpack by a given containerd version.)
