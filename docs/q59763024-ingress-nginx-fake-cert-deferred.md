## What the thread is about
Helm chart `nginx-ingress` (controller `quay.io/kubernetes-ingress-controller/nginx-ingress-controller:0.27.1`) on CentOS 8, Kubernetes 1.17, containerd 1.2.0; the same chart worked on CentOS 7 with Docker. The controller exits with `F ssl.go:389 unexpected error storing fake SSL Cert: could not create PEM certificate file /etc/ingress-controller/ssl/default-fake-certificate.pem: ... permission denied`. Removing the `securityContext.capabilities` block (`drop: [ALL]`, `add: [NET_BIND_SERVICE]`) makes the pod start. The question was edited later to add the deployment (`runAsUser: 101`, `allowPrivilegeEscalation: true`, drop ALL + add NET_BIND_SERVICE) and a second error: `nginx: [emerg] bind() to 0.0.0.0:80 failed (13: Permission denied)`. The one answer (+10) says to set `runAsUser: 101`; the asker replied that 101 "is not working". The thread does not give a verified fix for the final state, so the case is an adaptation, not a reproduction (stated in task.txt).

## What was built
Private containerd node (version-3 config, private socket/root/state, NRI off), CRI pod on host network, no kubelet. A small controller image built offline as an OCI layout: busybox httpd, `/etc/ingress-controller/ssl` owned 33:33 mode 775, busybox WITHOUT a file capability, `/entry.sh` that copies the template certificate and execs httpd on port 80. Run as uid 101 with drop ALL + add NET_BIND_SERVICE. Two stacked causes, the second hidden by the first: (1) the cert directory is not writable by 101; (2) after that `httpd: bind: Permission denied` because the program has no file capability.
Reference fix (deployment files + around the image, image untouched): `supplemental_groups: [33]` and a copy of the same busybox with `security.capability` (cap_net_bind_service=+ep) mounted over `/bin/busybox` from the root fs, then `node-apply`.
Oracle: exactly one READY pod, running container from the recorded image id, `/healthz` ok, uid/gid 101 without group 0, CapBnd exactly NET_BIND_SERVICE (0x400), not privileged, `/proc/PID/exe` is the recorded busybox, only allowed mounts (/bin/busybox, /etc/ingress-controller[/ssl]), listener on :80 is the container, certificate sha and CN match; host sysctl, images and node files unchanged; the check is repeated after `node-apply`.
Samples (14): reference_solution + 2 alternatives (ssl dir owned by 101 on the host + capped copy; whole /etc/ingress-controller from host mode 1777) pass; no-op, group 33 only, capped program only, run as 33, run as root, privileged, wider cap set (CHOWN added), sysctl lowered, entry.sh replaced by a mount, own server on the host, pod made by hand (deployment files unchanged) fail.

## Measured facts (sandbox containerd 2.4.2, VM containerd 2.2.1)
- A layer tar with PAX record `SCHILY.xattr.security.capability` (20 bytes `\x01\x00\x00\x02\x00\x04\x00\x00` + 12 zero bytes) is applied by containerd's unpack.
- uid 101 with drop ALL + add NET_BIND_SERVICE on host network binds port 80 only if the binary has the file capability. `no_new_privs` is not the cause. containerd 2.x CRI clears ambient caps (`add_ambient_capabilities` accepted and ignored), so ambient is no fix.
- Image dir 33:33 mode 775 gives uid 101 "Permission denied"; `supplemental_groups: [33]` fixes it. Root with drop ALL cannot write it either (no DAC_OVERRIDE).
- A capped binary must be mounted from the root fs, not `/run` (nosuid/noexec tmpfs).
- `ctr images mount` fails on containerd 2.2.1 (mount manager "no such device"; `--rw` "bucket already exists"): read image layers with `ctr content get` instead.
- Lowering `net.ipv4.ip_unprivileged_port_start` is a host change and is rejected; cleanup restores it from a saved copy.
