# q59463038 — CoreDNS cannot start with CRI-O and SELinux on (CentOS 7, CRI-O 1.16.1, Kubernetes 1.16.3) (filesystem) — DEFERRED

Status: deferred by the user (2026-10-24). Nothing was built (no case files, test suite, fixtures or docs-index entries).

## What the thread is about
CoreDNS pods go to Error/CrashLoopBackOff on a kubeadm cluster with CRI-O. audit.log shows `avc: denied { read | open }` for comm="coredns": `Corefile` (ConfigMap volume below /var/lib/kubelet/.../volumes/, target type `var_lib_t`) and the service-account `token` (projected volume, target type `tmpfs_t`), source type `container_t`. Answers: (1) rhatdan: `chcon -R -t container_file_t /var/lib/kubelet/.../volumes` (labels the volumes for containers), plus possibly `allow container_t tmpfs_t:file open;` for the secrets; (2) Dawid Kruk: reproduced on kubelet 1.16.4 and not on 1.15.7 (kubelet 1.16 stopped relabeling the volumes, upstream issue "SELinux volumes not relabeled in 1.16"); in enforcing mode the CoreDNS log says `open /var/run/secrets/kubernetes.io/serviceaccount/token: permission denied`; the asker found 1.16.5, 1.16.6 and 1.17.0 not fixed either; (3) the asker: `semanage fcontext -a -t container_file_t "/var/lib/kubelet/pods/<pod id>/volumes(/.*)?"` then `restorecon -R -v`. The asker's own broad `allow container_t var_lib_t:file { open read }` module is what he does not want (it widens access).

## Mechanism and a caveat
Files that a container mounts must carry a label that `container_t` may read (`container_file_t`); the kubelet/runtime normally relabels volumes (the `:z`/`:Z` effect), and the 1.16 kubelet did not for ConfigMap and projected volumes. The AVC lines in the question all have `permissive=1`: the system was in permissive mode when they were logged, so they show what enforcing mode would deny but do not prove that those denials made CoreDNS exit; the crash with `permission denied` is from the enforcing reproduction in answer (2).

## Why it was not built
- The sandbox has SELinux compiled in (CONFIG_SECURITY_SELINUX, default LSM selinux) and `selinuxfs` mounts, but no policy is loaded (`enforce` 0, current context `kernel`), there is no /etc/selinux, no /usr/share/selinux, no checkpolicy and no package source, so no policy can be loaded or relabeled; nothing like an AVC can be produced.
- The VM is Ubuntu 22.04 with AppArmor as its LSM. Enforcing SELinux there needs the boot parameters `selinux=1 security=selinux`, a relabel of the whole file system and a REBOOT, and a policy with the types `container_t`, `container_file_t`, `var_lib_t`, `tmpfs_t` plus the container rules; those come from RHEL/Fedora's container-selinux, not from Ubuntu's reference policy, so it would have to be compiled by hand. A runner that runs setup and cleanup for every sample cannot reboot the machine, and changing the shared VM's LSM is outside what a case may do.
- The thread's versions (CentOS 7.6, CRI-O 1.16, kubelet 1.16) are not available on the project's hosts, and `chcon`/`restorecon` fail on a host without SELinux, so even a configuration-level variant (as `configuration/q72879219`, which says real labels need an SELinux host) cannot test the labels.
- Coverage: no case has a real SELinux host; q72879219 is a config-level variant only.

## If it is taken up later
Needs an SELinux-enforcing VM image (CentOS/Rocky/Fedora with container-selinux, or a prepared Ubuntu image with a compiled policy) that does not need a reboot inside the run, with fixed CRI-O and kubelet/policy versions. Bad controls: a ConfigMap volume labeled `var_lib_t` and a projected token on `tmpfs_t` with `container_t` (confirm the real EACCES and the CoreDNS failure in ENFORCING mode first, not just AVC lines from permissive mode). Oracle: SELinux stays enforcing; CoreDNS reads the Corefile and the token and answers a controlled DNS query; after a new volume or a rotated token it still works; a directory with an unrelated wrong label is still denied; no broad `allow` rule and no `setenforce 0`.
