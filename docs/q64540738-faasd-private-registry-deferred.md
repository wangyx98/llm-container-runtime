# q64540738 — Faasd: can't pull image from private registry (configuration) — DEFERRED

Status: deferred by the user (2026-10-22). Nothing was built; the findings below were measured in the sandbox and then cleaned up (no leftovers).

## What the thread is about
`POST /system/functions` on faasd (OpenFaaS on containerd) with `registryAuth` in the body fails with `unable to pull image <registry_ip>/functions/functionName:<version>: cannot pull: failed to resolve reference "...": no scope specified for token auth challenge`. Docker pulls from the same registry fine. The registry type and the faasd version are not given. The only answer (not accepted, 8 votes): copy `~/.docker/config.json` to `/var/lib/faasd/.docker/config.json`. The root cause of the reported error is never confirmed by anyone.

## What was measured (faasd 0.10.0 / 0.11.0 / 0.13.0 binaries from the GitHub releases, a private containerd 2.3.6 at /run/containerd/containerd.sock, a stand-in registry with a TLS listener, real CNI plugins v0.8.5)
- The exact error is reproduced by faasd 0.10.0 (contains containerd v1.3.2; 0.11.0 has the same dependency) when the registry answers the manifest HEAD with a Bearer challenge WITHOUT `scope` (`Bearer realm=...,service=...`). The deployment API answers HTTP 400 with the question's text. containerd 1.3.x raises the error in `generateTokenOptions` when the challenge is parsed, before any credential is used.
- config.json does NOT fix that error in 0.10.0: with a valid `auths` entry for the registry the registry log still shows a single anonymous HEAD and no token request, for a bare scope-less Bearer challenge as well as for Basic + Bearer(no scope) in either order. So the thread's answer does not address the error of the question on that version.
- With a challenge that carries the scope, config.json is what makes the pull work: without it the pull ends with `pull access denied ... insufficient_scope: authorization failed`; with it the token service gets `GET /token?scope=repository:functions/fn1:pull` with Basic credentials, the manifest and both blobs are served, the deploy API returns 200, and `GET /function/fn1` on the provider returns the function's marker (needs `/usr/local/bin/faasd` for the log binary and the CNI bridge plugins).
- faasd 0.13.0 (containerd 1.5.4) does not fail on a scope-less challenge (the scope comes from the request): with config.json the pull and the deployment succeed. So the reported error is bound to the faasd version; "upgrade faasd" fixes it, config.json alone does not.
- Source facts (faasd master and 0.10.0): the deploy handler never uses `registryAuth`; `PrepareImage` reads credentials only from the fixed directory `/var/lib/faasd/.docker/` (not `DOCKER_CONFIG`) and only when `config.json` exists there; with the file present faasd builds its own resolver (`docker.ConfigureDefaultRegistries` + the authorizer) whose scheme is https for an IP registry, so the stand-in registry must serve TLS and the provider needs `SSL_CERT_FILE`.

## Why it was not built
- No design is both faithful to the reported error and solved by the thread's answer: keeping the scope-less Bearer challenge on 0.10.0 makes the answer's fix ineffective; a scoped challenge changes the error to `insufficient_scope` (a different failure than the question's); replacing the registry challenge by a plain Basic 401 reproduces neither.
- Cost is high: faasd hard-codes `/run/containerd/containerd.sock`, `/opt/cni/bin`, `/etc/cni/net.d`, `/var/lib/cni`, `/var/lib/faasd`, `/usr/local/bin/faasd`; function networking needs real CNI plugins and creates the host bridge `openfaas0` and iptables chains `CNI-FORWARD`/`CNI-ADMIN` (CNI does not delete the bridge: cleanup must); a TLS registry, an HTTP function image and a refusal check for those fixed paths are also needed. It all runs in the sandbox, so it is a matter of cost, not of feasibility.
- Coverage overlap: node-held registry credentials are in q67635227 and q76136482, kubelet pull secrets in q64935442, CRI-O in q77827486. What faasd would add is only "the provider reads one fixed config.json and ignores `registryAuth`" (weak runtime increment).
