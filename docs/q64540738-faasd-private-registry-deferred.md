# q64540738 — Faasd: can't pull image from private registry (configuration) — was DEFERRED, now BUILT (variant A, see the UPDATE at the end)

Status: deferred by the user (2026-10-22); nothing was built at that time; the findings below were measured in the sandbox and then cleaned up (no leftovers). Built on 2026-11-19 as the exact-error variant: see the UPDATE section at the end.

## What the thread is about
`POST /system/functions` on faasd (OpenFaaS on containerd) with `registryAuth` in the body fails with `unable to pull image <registry_ip>/functions/functionName:<version>: cannot pull: failed to resolve reference "...": no scope specified for token auth challenge`. Docker pulls from the same registry fine. The registry type and the faasd version are not given. The only answer (not accepted, 8 votes): copy `~/.docker/config.json` to `/var/lib/faasd/.docker/config.json`. The root cause of the reported error is never confirmed by anyone.

## What was measured (faasd 0.10.0 / 0.11.0 / 0.13.0 binaries from the GitHub releases, a private containerd 2.3.6 at /run/containerd/containerd.sock, a stand-in registry with a TLS listener, real CNI plugins v0.8.5)
- The exact error is reproduced by faasd 0.10.0 (contains containerd v1.3.2; 0.11.0 has the same dependency) when the registry answers the manifest HEAD with a Bearer challenge WITHOUT `scope` (`Bearer realm=...,service=...`). The deployment API answers HTTP 400 with the question's text. containerd 1.3.x raises the error in `generateTokenOptions` when the challenge is parsed, before any credential is used.
- config.json does NOT fix that error in 0.10.0: with a valid `auths` entry for the registry the registry log still shows a single anonymous HEAD and no token request, for a bare scope-less Bearer challenge as well as for Basic + Bearer(no scope) in either order. So the thread's answer does not address the error of the question on that version.
- With a challenge that carries the scope, config.json is what makes the pull work: without it the pull ends with `pull access denied ... insufficient_scope: authorization failed`; with it the token service gets `GET /token?scope=repository:functions/fn1:pull` with Basic credentials, the manifest and both blobs are served, the deploy API returns 200, and `GET /function/fn1` on the provider returns the function's marker (needs `/usr/local/bin/faasd` for the log binary and the CNI bridge plugins).
- faasd 0.13.0 (containerd 1.5.4) does not fail on a scope-less challenge (the scope comes from the request): with config.json the pull and the deployment succeed. So the reported error is bound to the faasd version; "upgrade faasd" fixes it, config.json alone does not.
- Source facts (faasd master and 0.10.0): the deploy handler never uses `registryAuth`; `PrepareImage` reads credentials only from the fixed directory `/var/lib/faasd/.docker/` (not `DOCKER_CONFIG`) and only when `config.json` exists there; with the file present faasd builds its own resolver (`docker.ConfigureDefaultRegistries` + the authorizer) whose scheme is https for an IP registry, so the stand-in registry must serve TLS and the provider needs `SSL_CERT_FILE`.

## Why it was not built (at the time)
- No design is both faithful to the reported error and solved by the thread's answer: keeping the scope-less Bearer challenge on 0.10.0 makes the answer's fix ineffective; a scoped challenge changes the error to `insufficient_scope` (a different failure than the question's); replacing the registry challenge by a plain Basic 401 reproduces neither.
- Cost is high: faasd hard-codes `/run/containerd/containerd.sock`, `/opt/cni/bin`, `/etc/cni/net.d`, `/var/lib/cni`, `/var/lib/faasd`, `/usr/local/bin/faasd`; function networking needs real CNI plugins and creates the host bridge `openfaas0` and iptables chains `CNI-FORWARD`/`CNI-ADMIN` (CNI does not delete the bridge: cleanup must); a TLS registry, an HTTP function image and a refusal check for those fixed paths are also needed. It all runs in the sandbox, so it is a matter of cost, not of feasibility.
- Coverage overlap: node-held registry credentials are in q67635227 and q76136482, kubelet pull secrets in q64935442, CRI-O in q77827486. What faasd would add is only "the provider reads one fixed config.json and ignores `registryAuth`" (weak runtime increment).

## The two variants that were offered
(1) credentials variant: faasd 0.13.0 + a TLS private Bearer registry with the correct scope (the error text becomes `insufficient_scope`, to be stated in task.txt), reference = config.json, oracle = deploy through `/system/functions`, invoke `/function/<name>` and get the marker, token request scope `repository:<repo>:pull` with Basic from the account, anonymous control fails, image removed and a new build published before the check; (2) exact-error variant: faasd 0.10.0 + scope-less Bearer challenge, reference = replace the provider by >= 0.13 and create config.json (differs from the thread's answer) — THIS ONE WAS BUILT. Pitfalls found: a kill pattern containing the registry script name kills the tool's own shell (use a script file with a bracket pattern); the default resolver of faasd 0.13 without config.json talks plain HTTP to loopback addresses (connection reset by a TLS listener).

## UPDATE (2026-11-19): BUILT as the exact-error variant (A)
Status: built and verified in the sandbox (root and non-root, containerd 2.4.2 and the 2.2.1 release binary); VM (aarch64, cgroup v2, Docker present) pending. Files: `cases/configuration/q64540738/`, `src/test_suites/configuration/q64540738.py`, `samples/fixtures/configuration/q64540738.json` (14 samples).

Design (as chosen by the user): faasd 0.10.0 provider + a TLS Bearer registry stand-in whose challenge has no scope; the deployment API (`POST /system/functions` on port 8081, basic auth, `registryAuth` in the body) answers HTTP 400 with the thread's text. Reference fix = release 0.13.0 AND `/var/lib/faasd/.docker/config.json` with the registry account (this differs from the thread's answer; task.txt says so). The oracle deploys both tags after removing them from containerd, calls them through `/function/<name>` and reads the registry's log for the token flow.

Lab choices worth keeping: containerd and the provider run in a private mount namespace (holder process + `nsenter`, started by `faasdctl`) in which only `/run/containerd`, `/opt/cni/bin`, `/etc/cni/net.d`, `/var/lib/cni` are the case's own; `/usr/local/bin/faasd` and `/var/lib/faasd` are real host paths (the solver edits them naturally; setup refuses to run if they exist, cleanup removes them only by marker or by the sha256 of a known release binary). Pinned downloads (sha256, cached in `/var/cache/bench64540738`, kept by cleanup): faasd 0.10.0 / 0.13.0 (amd64 and arm64), CNI plugins v0.8.5. Cleanup removes the bridge `openfaas0`, its veths, the iptables rules for 10.62.0.0/16, the chains `CNI-FORWARD`/`CNI-ADMIN` only if they did not exist before, restores `ip_forward`, and removes the mount-point directories it had to create.

New measurements (sandbox): (1) faasd 0.13.0 first POSTs `/token` (OAuth2 password grant); the registry must consume the body and answer 405, then the client falls back to `GET /token?scope=repository:<repo>:pull&service=...` with Basic. (2) 0.13.0 reads `config.json` at each deployment (no restart needed), but the provider binary only at start. (3) Only the base64 `auth` field is read: `username`/`password` fields are ignored; the host key must carry the port (`10.66.54.40` without it does not match; `https://10.66.54.40:15064` does); `~/.docker/config.json` is not read. (4) A function that runs as PID 1 and ignores SIGTERM makes the provider's DELETE wait 30 s and answer 500: the function programs install a SIGTERM handler. (5) `ctr images rm --sync` removes the content too, so the oracle sees the blob requests. (6) Python 3.13 verifies the CA: it needs `basicConstraints=CA:TRUE` and `keyUsage=keyCertSign` on the CA and SAN/EKU on the leaf.
