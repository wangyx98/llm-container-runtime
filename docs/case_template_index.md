# Case template index: which finished case to copy from

Every case has the same five stages (cleanup, setup, precondition oracle, the solution, postcondition oracle, cleanup) and the same files:
`cases/<category>/<id>/{task.txt,setup.sh,precondition.sh,reference_solution.sh,oracle.sh,cleanup.sh}`, optional `helpers/`, plus
`src/test_suites/<category>/<id>.py` and `samples/fixtures/<category>/<id>.json`. This page says, for each kind of problem, which finished
case to open first, so a new case starts from one working case instead of from a survey of all of them. Read that case's `setup.sh`,
`cleanup.sh`, `helpers/lab.py` and the generator of its samples; read nothing else unless the pattern below is not enough.

**Scope.** This index is built from the Diagnostics cases, which are the ones that were worked through in detail, plus the few other cases
whose notes are in `docs/`. The other categories (compatibility, configuration, filesystem, isolation, networking) have many finished cases (isolation has its first detailed rows now: q66547508, q66478456, q56996594, q74592511, q76608572, q75294704, q72968351; networking has its first: q74243015, q71671179, q79305194, q72528378, q65724285, q60208766, q61054998, q78821163, q78631941, q60714937, q73394153, q70704948; compatibility has its first: q65650082, q75845783, q73434226, q70231694, q59724108, q63457756, q68845002, q72120811, q73029815, q77044676, q76466526, q66733729, q71499683, q54365253, q77040211, q66512464, q53435138, q37420728; configuration has its first: q59744000, q62675268, q72094271, q66642654, q49877639, q77827486, q78402595, q76136482, q72879219, q67635227, q64935442, q54303822, q62439583)
that are not listed here yet. Add a row, and what it gives you, when you next build or revisit a case of those kinds, after reading that
case, so every row stays something that was checked.

Task wording: follow `docs/task_authoring_checklist.md` (no placeholders, literal names, one sentence on allowed tools, the sudo sentence, end
with "Return the commands needed to complete the task.").

## 2. What to copy, what to change

Copy the whole case directory, then change:

1. `CASE_ID` / `bench<id>` in every script, and every path under `/run`, `/var/lib` and `/tmp` that contains it. The case id is the only thing
   that keeps a case from touching another one's state.
2. `task.txt` and the shape of the file the solution writes (`verify.py` and `oracle.sh` follow from it).
3. `lab.py`: what is created, what is recorded in `truth.json` (from what the lab made and from `/proc`, never from the solution's tools),
   and what `more` changes after the solution has run.
4. The generator of the samples (keep it in a scratchpad, not in the repo): one correct reference, one valid alternative, a no-op, then wrong
   samples each aimed at one `verify.py` branch.

Keep as is: `cleanup.sh` (kill by `comm` plus a command-line regex, unmount deepest first, remove recorded runc state), the start of
containerd with `setsid -f`, the helper-hash check in `precondition.sh` and `oracle.sh`.

## 3. Sample design rules (what has worked)

- Every wrong sample exercises a **different** oracle branch; do not add two that fail at the same line.
- A replay or hard-coded sample is defeated by a change the oracle makes after the solution has run (`lab.py more`).
- A sample that changes the node (removes a pod, prunes containers) is caught by `lab.py check`, which runs before and after reading.
- A guess by name (for example, every process called `pause`) should look right for the first run and fail for the added one.
- Failure lines are short; anything of variable length goes last (the harness keeps about the last 500 characters of the oracle's output).
- Typical size: 9 to 11 samples.

## 4. Pitfalls already paid for

- `crictl` defaults to the CRI-O socket: always pass `--runtime-endpoint` **and** `--image-endpoint`. Flags such as `-o json` go before the
  positional arguments (`crictl inspectp -o json ID`).
- `crictl` shows `unknown` for pod and namespace unless the pod and container configs carry the kubelet labels
  (`io.kubernetes.pod.name`, `io.kubernetes.pod.namespace`, `io.kubernetes.pod.uid`, `io.kubernetes.container.name`).
- `crictl logs` reads only the current log file of a container: what the log rotation moved away is not in it. A rotated log is `N.log.TIMESTAMP`
  (timestamps sort in time order); all but the newest rotated file are gzipped. A record is `TIMESTAMP STREAM TAG TEXT`, TAG `P` for a part of a
  line that goes on in the next record (a write over 16 KiB), `F` for the end of a line.
- The image ID the CRI shows is the digest of the image config. `crictl inspecti -o json ID` has the config as the CRI reads it in
  `info.imageSpec` (`created` is absent when the config has none; timestamps come back in Go's form: nine-digit fractions without trailing zeros,
  `Z` or a numeric offset). `crictl images` lists images of the namespace `k8s.io` by `repoTags`; a name added there with `ctr -n k8s.io images tag`
  appears in the CRI without a restart. The blobs of an import and the image record are as old as the import, whatever the config says.
- A restarted container is a NEW container (same name, next attempt number, its own log file `ATTEMPT.log`): the newest container of a name is
  not the one asked for. `crictl ps -a --name '^NAME$'` lists all attempts, newest first; `crictl inspect` gives `status.logPath`, `exitCode`, `reason`.
- `ctr` 2.x prints a cgroup-v1 deprecation warning on stderr: use `2>/dev/null` where its output is parsed.
- An imported (not pulled) image has no repo digest in `crictl`; the CRI plugin also adds `sha256:` entries for it in `k8s.io`.
- systemd 249: `journalctl -u UNIT --after-cursor` drops one line when the cursor entry is not selected by the unit filter; put cursors on
  entries of the unit itself. containerd logs an error and "stop pulling image" from different goroutines, in no fixed order.
- CRI namespace modes: `namespace_options` is an enum with POD = 0 (the default), CONTAINER = 1, NODE = 2. Set `pid: 1` in the pod AND in each
  container config to get what the kubelet gives (a PID namespace per container); with the default all containers of a pod share one PID namespace
  with the pause process as its first process (which then takes over the orphans, and a container's first process is not PID 1). Unset `network` is
  POD (a netns of its own: it needs a CNI plugin, see q71482106).
- A container's processes are in a cgroup `/k8s.io/<container id>` (cgroup v1 on every controller line, v2 on the one `0::` line): the 64
  hexadecimal characters are in `/proc/PID/cgroup` for every descendant. `/proc/PID/environ` and `ns/*` of a root-owned process need root: in a
  script run by a normal user, `sudo cat FILE | ...`, never `sudo cmd < FILE` (the redirect runs as the user).
- Plain `ctr` (no CRI): a container's record (`ctr -n NS containers info ID`: `Image`, `Runtime.Name`, `Labels`, `Spec.process.env`, `Spec.mounts`) has
  nothing about the task; `ctr -n NS tasks ls` has `TASK PID STATUS` (RUNNING, STOPPED, ...), and a container with no task is not in it. A task whose process
  was killed stays STOPPED with its old PID until `tasks delete`. `Labels` also holds labels of the image config (`io.containerd.image.config.stop-signal`,
  image labels): compare the labels the lab set, not the whole object. `ctr containers info --spec ID` prints only the spec. `ctr tasks start ID` without
  `-d` stays attached (it blocks the tool); use `-d`. `ctr containers label ID` with no label is an error.
- runc keeps its state below `/run/containerd/runc/<containerd namespace>/<container id>`, shared by every containerd of the machine: name the namespaces
  of a case `bench<id>-...` so cleanup removes `/run/containerd/runc/bench<id>-*` and never another containerd's directory.
- The PID of a container's first process, independent of ctr: the child of the `containerd-shim` process whose command line has `-namespace NS -id ID`.
- Log collectors in the kubelet layout: a CRI log file is written by containerd as `TIMESTAMP STREAM F|P TEXT` (the timestamp has the host's UTC
  offset, not always `Z`; `P` marks a part of a line longer than 16384 characters). The directory of `log_path` is made by the runtime; the
  `containers/` symlinks are made by the kubelet, so the lab makes them. With the Docker JSON parser on such a file every line of a Fluent Bit
  `tail` input fails to parse and comes out as `{"log": WHOLE_LINE}`; with a `cri` regex parser (`stream`, `log` captured) or the tail input's built-in
  `multiline.parser cri` it comes out as `{stream, log}`. A `Parser` name that `Parsers_File` does not define stops Fluent Bit at start.
- Fluent Bit and the Fluentd gem cannot be fetched in the Claude sandbox (packages.fluentbit.io and index.rubygems.org are blocked by its egress
  policy): a case that runs them is verified for real on the VM. In the sandbox a stand-in (not committed) that implements only the used part of
  the configuration (`FLUENT_BIT_BIN` points to it; its comm must be `fluent-bit`, so use `#!/usr/bin/python3`, not `env`) exercises the lab, the
  collector and every branch of the oracle.
- Never `pkill -f` a pattern that appears in your own command line; kill by exact `comm` and check the command line. The same goes for
  `kill_ours bash`: the shell running the test, or the tool's own `bash -c` with the case's paths in its text, matches `$WORK_DIR` and is killed.
  Start a long-lived host process with `exec -a PATH-IN-WORK_DIR sleep N` so it is a `sleep` that `kill_ours sleep` can find.
- A killed containerd leaves the net namespace mounts of its pods in `/var/run/netns`; record the new entries when the pod starts and
  remove only those.
- Image programs must be static (`gcc -static`) and built offline; Docker Hub, `mirror.gcr.io` and some package hosts are blocked in the
  sandbox, so the lab imports images it builds itself (`mkimg.py`).
- The grammar of `ctr images list` filters (containerd `filters` package): the field is `name` (the ref); a field that does not exist, such as `ref`,
  lists nothing with status 0. `~=` is an unanchored regular expression, `==` and `!=` are exact, a comma inside one filter is AND, several
  filter arguments are OR. In a quoted value a backslash has to be doubled (`name~="bitnami/kafka:2\\.7\\.0"`; one backslash gives "illegal escape sequence"),
  quote any value that holds regular expression characters. The CRI plugin of `k8s.io` also adds `sha256:...` entries, so a case about names
  compares `images list -q` with the refs the lab imported. The filter goes to `ctr` as ONE argv element (it has no shell to quote it).
- A case that uses the real namespace name `k8s.io` for containers (the point of the question) shares `/run/containerd/runc/k8s.io/` with every other containerd of the
  machine: give the containers random 64-hex IDs, write each ID to `.bench/ids.txt` BEFORE creating the container, and let `cleanup.sh` remove only those directories
  (never the whole `k8s.io` directory, which may belong to a real node). In `k8s.io` the CRI plugin lists every imported image a second time under its bare ID
  (`sha256:...`); the lab leaves those entries out of its record and the oracle lets the solution list them or not.
- To forbid a connection to a second socket, put a listener there (`tap.py`) that logs and closes; checking it must not connect (no `ctr version`). A real second
  containerd would also work but gives nothing more: the mistake it catches is the call, not the data.
- `runc --root DIR list` creates DIR when it does not exist (even for `list`): a sample that tries a hardcoded root must test `isdir` first, or the sample leaves
  directories behind. The exec root of a private `dockerd` is not readable for the current user: read it with `sudo ls` / `sudo test` in `lab.py` and `precondition.sh`
  (the case passed as root and failed as the non-root user until then).
- Docker keeps its images in containerd only with the containerd image store (`--feature containerd-snapshotter=true`, Docker 24 or newer; the default of Docker 29):
  they are then in the namespace `moby` as `docker.io/NAME:TAG`, and Docker and `ctr` agree on the digest. With the classic graph driver containerd has none, so
  `lab.py` stops with a clear message when the image is not there. A private `dockerd` also leaves `/run/docker/plugins`, which any Docker host has.
- With one containerd shared by Docker and the CRI each client has its own set: Docker deletes a container from containerd when it stops, so `ctr -n moby containers ls` shows the
  RUNNING Docker containers only while `docker ps -a` shows all; the CRI keeps exited containers, and its pod sandbox is a container of containerd in `k8s.io` that `crictl ps` does not
  list (`crictl pods` does). The containers of a pod run in the sandbox's shim (its `-id` is the sandbox ID), so the "child of the shim started for this ID" PID of q67990667 only
  works for plain `ctr` and Docker containers; for CRI containers record `crictl inspect` `info.pid` once, with the start time from `/proc/PID/stat`, and compare that later.
- crictl 1.34 checks the image service too: give it `--runtime-endpoint` AND `--image-endpoint`, or it dials the default CRI-O socket and fails.
- `sudo rm -rf /run/containerd/runc/*/"$id"` does nothing for a user who is not root: `/run/containerd/runc` is root-only, so the glob is expanded by the user's shell and stays a
  literal `*`. Use `sudo sh -c 'rm -rf /run/containerd/runc/*/"$1"' _ "$id"` (as q48616250 does).

- Bare runc: `runc run -d` leaves the container's stdout/stderr attached to the runc process' pipes; start it from Python with the output sent to a FILE, not to `capture_output` (the container holds the pipe open for ever and `subprocess.run` never returns).
  `runc state ID` has the PID of the first process but no cgroup path (runc 1.1); the cgroup is in `/proc/PID/cgroup`. A relative or missing `cgroupsPath` is placed below the cgroup of whoever ran runc (`/ID` at the root in the sandbox,
  below the session scope on a systemd host), an absolute one is used as given; `runc delete -f` removes the container's cgroup but not the parent directory made for an absolute path: `cleanup.sh` removes `bench<id>*` directories
  with `sudo find /sys/fs/cgroup -maxdepth 8 -depth -type d -name 'bench<id>*' -exec rmdir {} \;`.
- CPU time of a cgroup: v1 `cpuacct.usage` is nanoseconds (the hierarchy may be mounted as `cpuacct` or `cpu,cpuacct`: find it in `/proc/self/mountinfo`), v2 `cpu.stat` `usage_usec` is MICROseconds and exists in a cgroup even when the cpu controller is not
  enabled for it; `runc events --stats` gives `data.cpu.usage.total` in nanoseconds on both. A host in hybrid mode (the sandbox) has both a v1 `cpuacct` mount and a unified mount at `/sys/fs/cgroup/unified`: decide the version by the `cpuacct` mount first.
  To test the v2 branch without a v2 host: `unshare -m bash -c 'umount -R /sys/fs/cgroup && mount -t cgroup2 none /sys/fs/cgroup && python3 run_single_case.py ID'` (the v1 mounts must be unmounted, not only covered: mountinfo still lists covered mounts).
- A process in a container whose root is root-owned but which has only runc's default capabilities (no `CAP_DAC_OVERRIDE`) cannot write into a directory owned by the user who runs the lab: `chmod 777` the control directory that is bind mounted
  (the case passed as root and failed as the non-root user until then). After `runc delete -f` the killed processes may be zombies for a few seconds in the sandbox (its PID 1 does not reap at once): a residue check of `pgrep -cx app` is only valid a few seconds later.
- A counter that grows with a process that is controlled by the lab can be verified exactly: the worker reports the CPU time it used (`CLOCK_PROCESS_CPUTIME_ID`) and the counter of its cgroup must grow by that (plus a little polling), so the oracle needs no tolerance for noise
  on the machine; make the other container (not the target) work in a separate window to catch a counter that holds both (the parent cgroup).

- Docker 29 (containerd image store by default) does NOT start a containerd of its own: without `--containerd` / `"containerd"` in `daemon.json` it dials `/run/containerd/containerd.sock` and `docker run` fails with "connection refused"; the
  classic store (`"features": {"containerd-snapshotter": false}`) does not help. A private `dockerd` therefore always needs a private containerd (q57009928's start). Every `dockerd` option except `--host` can sit in `daemon.json`
  (`--config-file`); an option named both on the command line and in the file is an error.
- Never prove "nothing shows runtime-root" with `ps aux | grep -c ...`: the command line of the shell that runs the check (or of a tool call that quotes the word) matches. Look at the command lines of the processes by NAME
  (`pgrep -x dockerd`) instead. And never run `runc --root SOMEDIR list` in a precondition for a directory that may be real (`/var/lib/docker/containers`): runc creates a missing root.
- A script that hardcodes Docker's usual root (`/var/run/docker/runtime-runc/moby`) must test `-d` first (the sample), or it leaves the directory behind; on a host with a system Docker the directory exists and the precondition checks that it holds nothing.

- Isolation with a user namespace (q66547508): (1) a mapped root cannot create anything in a rootfs owned by host root (`mkdir .../rootfs/proc: permission denied`): `chown -R` the rootfs, the data dir and every bundle parent the
  mapped id must pass to THE MAPPED HOST ID, numerically, and keep the bundle under `/var/lib` (not a `noexec` `/tmp`). (2) Mounting `sysfs` needs `CAP_SYS_ADMIN` over the network namespace it shows, so a user namespace with the HOST's network
  namespace gets `operation not permitted` at `/sys`; the allowed forms are no `/sys` mount, or a bind of the host's `/sys` (`rbind,nosuid,noexec,nodev,ro`; the cgroup mount below it comes along with `rbind`). A reference that drops the
  `/sys/fs/cgroup` mount as well is the same on cgroup v1 and v2. (3) `ctr`'s `--uidmap/--gidmap/--net-host` cannot express either fix: build the case on runc and say so in `task.txt` (the tools line names what is allowed).
  (4) `runc run -d` keeps the container's stdio on runc's pipes: the solution and the reference redirect `</dev/null >/dev/null 2>&1`, and `task.txt` tells the model to. (5) Prove the claim "inside root is host 5000" from the host side
  (`/proc/PID/uid_map`, the owner of `/proc/PID`, a file the program wrote is owned by 5000), and the claim "host network" with the inode of `/proc/PID/ns/net` against `/proc/self/ns/net`; a `tmpfs` at `/sys` and a read-write bind of `/sys`
  are separate wrong samples (`mountinfo` fstype and options).

- Rootless containerd under rootlesskit (q56996594): (1) `--copy-up=/run` leaves SYMLINKS to what exists on the host: `/run/containerd` of a rootful daemon (and `/run/nri`) point at root-owned directories, so containerd's plugins fail (`mkdir ...: permission denied`, `transfer` service unknown) or it dies on the NRI socket:
  `rm -f /run/containerd` inside the child before `exec containerd` (what dockerd-rootless.sh does) and `disabled_plugins = ["io.containerd.grpc.v1.cri", "io.containerd.nri.v1.nri"]`. (2) `ctr` must run in the child's namespaces
  (`nsenter -U --preserve-credentials -m -t $(cat STATE_DIR/child_pid) ctr --address SOCK ...`): the FIFOs of `ctr run` live under the child's `/run`. (3) The container's cgroup must be below the user's delegated one:
  `ctr run --cgroup NAME` (relative), not the default `/default/ID`; and `ctr run` asks for `cpu.shares` 1024 by default, which runc writes as `cpu.weight`: on a distribution that delegates only `memory pids` to users (Ubuntu) that fails with
  `error setting cgroup config for procHooks process: openat2 .../cpu.weight: no such file or directory`: `--cpu-shares 0` leaves it out (the reference does; the sandbox is cgroup v1 and cannot show it). (4) Judge "not root" from the host: `Uid:`/`Gid:` of `/proc/PID/status` are the host's IDs, `ns/user` differs from the checker's own (`/proc/1/ns/user` is
  not readable in the sandbox), `uid_map`/`gid_map` start `0 <user> 1` and `1 <start of /etc/subuid> 65536`; root of the checker may have to `cd` into a root-only dir through `sudo bash -c`, not in the harness user's own shell.
  (5) A set-uid copy of `ctr`, a group of a rootful socket, a sudoers rule and a changed socket mode are the shortcuts: group/sudo/socket mode are checked statically, the set-uid copy only shows in the process (`containerd-shim` as host 0).
  (6) `userdel -r` fails while the user manager or any process of the user (or of its subordinate IDs) lives: `disable-linger`, `terminate-user`, `pkill -u`, kill by ID range first.
  (7) Do not assume rootlesskit/uidmap are preinstalled (the VM had neither): `setup.sh` installs the Ubuntu packages `rootlesskit uidmap` when a tool is missing (like gcc) and stops with the install command if that fails; on Ubuntu 24.04 an AppArmor restriction on unprivileged user namespaces (`kernel.apparmor_restrict_unprivileged_userns`) shows up as the precondition's rootlesskit control failing, not as a model failure. (8) The sandbox has no systemd, rootlesskit or uidmap (apt and the Go proxy are blocked): the case was verified with sandbox-only stand-ins (`loginctl`, `systemctl --user`, `rootlesskit`, `newuidmap`, a delegated cgroup) kept outside the repo; the first run on the VM is the check of the real tools.

- A root-only daemon socket given to one user (q74592511; same mechanism as q70714501): (1) The change must come from the daemon's config (`[grpc] gid`/`uid` in `/etc/containerd/config.toml`; `containerd config default` is version 3 and has a `[grpc]` section with `uid = 0`, `gid = 0`): a live `chgrp`/`chmod` is lost at the next start, so the oracle restarts the daemon itself and tests again (a sample for it). (2) A socket that answers is a MANAGEMENT grant (create/stop/remove containers, pull/delete images): the task says "as few users as possible", the oracle keeps a second user out, and nothing says "read-only". (3) The check needs an independent truth: the lab imports a NEW image with a random name into the namespace the CRI shows (`ctr -n k8s.io images import`; the CRI lists only `k8s.io`) and asks `crictl images -o json` as the user: a canned or copied answer cannot contain it. (4) A stand-in `crictl` in `/usr/local/sbin` shadows the real one through sudo's `secure_path` without touching the system file; the oracle sees it by the missing probe image, and `cleanup.sh` removes only files that carry the case id. (5) The case edits HOST files (`/etc/containerd/config.toml`, `/etc/crictl.yaml`): setup copies them to `/var/lib/CASE` (mode 700) and cleanup puts them back (or removes them if they did not exist) and restarts the daemon; every test of a file there must use `sudo test -f` (a plain `[ -f ]` of the harness user silently says "no" and nothing is restored). Do not trust `/etc/crictl.yaml` when waiting for the CRI in setup: it may point at another runtime (CRI-O): write it first, or pass `-r`/`-i`. - Wildcard mirror and JFrog endpoints (q62439583): (1) containerd 2.3.6 and 2.2.3 honour the legacy `mirrors.'*'` as the default route (it is deprecated: the log says so and falls back to the local pull mode); an explicit entry such as `docker.io` wins over it, and `_default/hosts.toml` in a hosts directory behaves the same, so "the wildcard does not route k8s.gcr.io" of the 2020 thread is not reproducible and is not what the case tests. (2) A mirror endpoint with a PATH (Artifactory's repository path method, `/artifactory/api/docker/<repo>`) is used by the legacy `mirrors` as it is (no `/v2` added), by hosts.toml with `/v2` added: the lab uses one address per repository (the port method), which keeps `registry.configs.<HOST:PORT>.auth` able to hold one account per repository. (3) A 401 with a Basic challenge makes the CRI send the account of `configs` for the ENDPOINT's host:port; hosts.toml needs a Basic `Authorization` header per host (it works for Artifactory, which checks Basic itself, unlike the Bearer token services of q76136482). (4) `config_path` together with `mirrors`/`configs` leaves the node without a CRI plugin (nodectl cannot see it come up). (5) When the mirrors of a name fail, containerd falls back to the registry named in the reference (the real quay.io on a machine with network access: an existing public tag such as coreos/flannel:v0.11.0-amd64 then fails with a media-type error, not `not found`), so the case uses lab-only repository names and never checks the error text; a name with no entry goes to the real registry, which the check sees as no request in the stand-in's log.
- A LinuxKit-like node (q73341204): (1) `ctr run --rootfs` takes the root file system as the POSITIONAL argument (`--rootfs` is a flag) and gives the container no PATH (pass `--env PATH=...`, or `ctr task exec ... sha256sum` fails with `executable file not found in $PATH`); (2) containerd's runc shim appends the namespace to the root it is given: `--runc-root DIR` means `DIR/<namespace>` (default `/run/containerd/runc/<namespace>`), which is why the runc of the getty (default root `/run/runc`) lists only the containers runc started itself; (3) a `ctr task exec` / `runc exec` process joins the container's mount namespace, so a client that sends `/proc/self/ns/mnt` as its name proves where a command ran; (4) `grep` on a log line that contains `mnt:[4026...]` must use `-F` (the brackets are a regex).
- gVisor pods and CPU statistics (q63132692): (1) the answer's cause is the runsc release, not a setting: `runsc events --stats` has no `cpu` before 20210208.0, and the shim then reports 0 (CRI `usageCoreNanoSeconds` 0, `ctr tasks metrics` `cpuacct.usage 0`) while memory and PIDs are reported; (2) 20210208.0 reports a counter that is not the pod's (hundreds of seconds at the start, 2.5 core/s for a pod that uses one, 0 for the sleeping pod), 20220309.0 and later give the pod's own number (about 0.95 core/s for the busy loop): a check must compare a busy and an idle gVisor pod and the age of the counter, not only that it is not 0; (3) a newer runsc cannot read the state files of sandboxes created by an older one (`crictl stopp` fails with `json: cannot unmarshal number`), so the pods are removed BEFORE the release is switched; the shim and runsc are found in the PATH of containerd at every pod start, no restart is needed; (4) a new runsc with the host network cannot report events at all (`/proc/net/dev is not opened for hostinet`), so the lab uses `network = "none"` in runsc's file; (5) the shim lowers its own OOM score to -999 and fails to start without CAP_SYS_RESOURCE (restricted sandboxes): setup patches the node's COPY of the shim only where that capability is missing (never on a normal host); (6) the CRI needs a pod without `hostname` when it uses the node's network (`unable to set hostname without a private UTS namespace`); (7) the case is cgroup v1 ONLY: runsc before 2022 knows only cgroup v1 and on a cgroup v2 host fails at the first gVisor pod with `configuring cgroup: open /sys/fs/cgroup/cpu/<parent>/<id>/cpu.shares: permission denied` (it creates /sys/fs/cgroup/cpu/... and opens cpu.shares, which a v2 hierarchy does not have); the releases that run on cgroup v2 (2022-03 and later) all export the CPU, and containerd 2.x has no `disable_cgroup`, so there is no v2 variant of the symptom; setup.sh exits with NOT APPLICABLE on `cgroup2fs`.
- CRI-O metrics over TLS (q68471241): (1) measured with the official bundles: 1.20.7 and 1.21.0 log `Serving metrics on :PORT`, serve plain HTTP and ignore `metrics_cert` / `metrics_key` (`crio config` of 1.20 does not even list the two keys; a TLS handshake fails with `wrong version number`); 1.22.4 logs `Serving metrics on :PORT via HTTPs` and the validity of the certificate, answers a plain request with 400 `Client sent an HTTP request to an HTTPS server`; (2) with 1.22.4 a certificate path that does not exist stops CRI-O at its start (`Creating key pair reloader: load certificate ...`) and a drop-in without certificate and key serves plain HTTP (`via HTTP`): there is no self-signed fallback in this release, although the release notes of 1.22 mention one; (3) the CRI-call counters `container_runtime_crio_operations{operation_type="RunPodSandbox"|"CreateContainer"|"StartContainer"|"ListImages"|...}` are the proof that a metrics endpoint belongs to the node: read before and after a workload, they grow by exactly the calls made; (4) the listener of a TCP port is found through `/proc/net/tcp*` (state 0A) and the socket inodes in `/proc/*/fd`, which tells a CRI-O from a TLS proxy or a canned server without trusting its answers; (5) Python 3.13 verifies certificates strictly (the CA needs `keyUsage` with keyCertSign, the leaf needs subject/authority key identifiers), curl does not: make the lab PKI with those extensions; (6) a runc without CAP_SYS_RESOURCE cannot set the -998 oom_score_adj of a sandbox: a runc wrapper drops it only on such hosts (flag file made by setup); (7) a port in TIME_WAIT after the previous sample is free for a Go listener: the free-port test of setup uses SO_REUSEADDR.
- Exec-session disconnect (q78687277): (1) **containerd 2.3's CRI kills the exec process 0.5 s after its client dies**; the leak of the question exists on the 1.7 line, so the node is pinned to 1.7.20 (the boundary between the two was not bisected); (2) measured in the container: a **tty** exec session whose client is killed gives the process no passive signal at all - no POLLHUP, EOF, EIO, SIGHUP, no EPIPE or EIO on stdout writes, TIOCGWINSZ and `/dev/tty` fine, the shim holds both ends of the pty - except that about 126 KB of unread output fills the pty and a non-blocking write fails (EAGAIN); a session **without tty** gets POLLHUP (0x10) on stdin and read() = 0, stdout writes still succeed; (3) what a terminal emulator types reaches the tty process through the exec stream, so the way to detect a tty disconnect is to ask: write the cursor position query `ESC [ 6 n` and expect `ESC [ row ; col R` on stdin (raw mode); (4) `/dev/tty` is not an oracle (always openable in a tty session, ENXIO without tty); (5) a program's own report is proven by `SO_PEERCRED` on a unix socket in a bind-mounted directory: the kernel gives the peer's pid translated into the pid namespace of the one who asks, so a host-side collector sees the host pid, and a process of the container can be found by `NSpid` and an exact `cmdline`; (6) in a test client, `pty.fork()` + the answerer thread for the cursor query, and for pipes an open silent write end - closing it is a signal of its own; (7) `pkill -f` with a pattern that is in the own command line kills the own shell: enumerate pids and compare `/proc/PID/cmdline`.
- Snapshot -> image attribution (q77179505): (1) `ctr snapshot ls` / `container list` look at the namespace `default` only, kubelet and the CRI use `k8s.io`, Docker `moby`; the same layer imported into two namespaces is two snapshots in two numbered directories; (2) the directory of a committed snapshot is the first path in the mount of a temporary `ctr snapshots view` of it (a bind mount for a one-layer chain, `lowerdir=a:b` otherwise), of an active one the `upperdir` of `ctr snapshots mounts`; the key of a committed layer is the chain ID, `sha256("<parent chain> <diff_id>")` over the config's diff_ids; (3) ctr's snapshot, image and container commands create no lease: **a garbage collection can remove a view between `view` and `mounts`** (seen as a flaky `snapshot does not exist`), so the lab pushes the scheduler out of reach (`mutation_threshold`, `deletion_threshold`, `schedule_delay`, `startup_delay`); (4) the numbered directories of removed snapshots are deleted later by the collection: a state check must compare `ctr` lists and the files, not `ls snapshots/`; (5) `ctr snapshots prepare` takes `--snapshotter` before the subcommand (`ctr snapshots --snapshotter X prepare`), `ctr images import` unpacks by default (`--no-unpack` skips it), `ctr containers create` makes the writable snapshot with the container ID as key without any runtime; (6) the snapshotter's directory is root's: a solution run by a user needs `sudo find`, and a bash `[ -d ]` in setup needs `sudo test`; (7) an image keeps `history[].created_by` (and `empty_layer`), not the Dockerfile: the honest answer is a marked `unrecoverable` plus the history.
- Pull from a Harbor gives `unexpected media type text/html` (q75622952): (1) containerd 1.6's CRI takes the path of a mirror endpoint as the root of the registry API and adds `/v2` only when the path is empty (`https://host`) or `/v2/`; `https://host/` (trailing slash) requests `/<repo>/manifests/<tag>` with no `/v2`, `https://host/harbor` requests `/harbor/<repo>/...`; (2) a path outside `/v2/` is answered by Harbor's portal (single page application, `200 text/html` for any path); with no `Docker-Content-Digest` the descriptor of the "manifest" is the page itself, so the digest in `unexpected media type text/html for sha256:<digest>` is the sha256 of the page body, and the CRI error is exactly the question's; a failing CA is `x509: certificate signed by unknown authority`, never text/html, and the endpoint-less setup (no mirror entry) also works; (3) the cause (the slash) is an inference from the lab: the question has no HTTP response and the real config may differ; (4) containerd pulls from loopback addresses (127/8) over plain HTTP by itself, so a TLS registry in a lab needs a non-127 address (an alias of `lo` set with the SIOCSIFADDR ioctl, no `ip` binary); (5) `crictl images -q <name>` printed the other images in 1.34, so absence of an image is checked with `crictl inspecti`; (6) after `crictl rmi` containerd still fetches the blobs again, so the oracle requires the manifest requests, not the blob requests, in the log; (7) the Bearer flow works with a Basic account: containerd tries `POST /service/token`, a 405 sends it to `GET` with the account; (8) a sample that puts the CA into `/usr/local/share/ca-certificates` leaves it on the machine, so cleanup removes a file there that equals the lab CA and rebuilds the bundle.

## 5. How to verify a new case (the loop the series used)

1. Run every sample through `python3 run_single_case.py <bare id> --model NAME` (`--list` lists them); compare with the expected table.
2. Run the reference through a pty (`script -qec "..." /dev/null`) and as a non-root user with passwordless sudo.
3. Repeat the reference several times to catch flakes.
4. After `cleanup.sh`: no directories under `/run`, `/var/lib`, `/tmp` for the case id, no mounts, no processes, no entries left in
   `/var/run/netns` or in the shared runc root, compared with the count before the run.
5. The final report names: the loop command, the expected-results table, the residue commands, the helpers the case uses and whether each
   is necessary, and the commit message.
