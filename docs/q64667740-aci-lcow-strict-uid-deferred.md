# q64667740 — ACI: `failed to find user by uid: 10001: expected exactly 1 user matched '0'` for primekey/ejbca-ce (isolation) — DEFERRED, waiting for the original platform's artifacts

Status: deferred by the user (2026-11-01) after a feasibility check. Nothing was built (no case files, test suite, fixtures or docs-index entries).

## What the thread is about
An Azure Container Instances (ACI) group with the image `primekey/ejbca-ce:6.15.2.3` (Dockerfile ends with `USER 10001`, `CMD [".../standalone.sh", "-b", "0.0.0.0"]`; the image's `start.sh` appends a passwd entry `ejbca:x:10001:0:...` at start-up if `whoami` fails) stops at creation: `to create containerd task: failed to create container ...: guest RPC failure: failed to find user by uid: 10001: expected exactly 1 user matched '0': unknown`. The same image runs with local Docker (Ubuntu 20.04) and ran on ACI a few weeks earlier; no container logs because the process never started.
Answers: (1) uid 10001 is not in the image's `/etc/passwd`; add it at build time (`useradd -u 10001 ...`); (2) the message comes from the Microsoft opengcs/hcsshim guest (`setUserID` -> `getUser` -> `user.ParsePasswdFileFilter`, which insists on exactly one match), probably ACI moved the group to the LCOW (Hyper-V Linux guest) runtime; workaround: derive an image with `RUN echo "ejbca:x:10001:0:ejbca user:/opt:/sbin/nologin" >> /etc/passwd` (as root, then `USER 10001`). Azure support (a comment): the image "requires multiple users ... not supported on the container runtime", suggested pinning the subscription to the other infrastructure.

## Measured / checked on 2026-11-01
- Plain Linux containerd + runc does NOT fail. An image whose config has `User: "10001"` and whose `/etc/passwd` holds only root starts and prints `uid=10001 gid=0 name=(none)` with containerd 2.3.6 + runc 1.1.12 in the sandbox, with the ctr 2.3.6 client and with the ctr 1.7.20 client. The failure is not a general Linux-containerd behaviour.
- The strict lookup has been removed upstream. In hcsshim v0.9.0 (2021-10) `internal/guest/runtime/hcsv2/spec.go` still has `getUser` with `expected exactly 1 user matched`, but `setUserID` no longer returns the error: when no passwd line matches it sets `UID=uid, GID=0`. The v0.8.12 tag has no guest code at all (it was in the separate opengcs repo then). So the reported behaviour belongs to a 2020 ACI guest, not to current LCOW.
- Docker Hub is not reachable from the sandbox (token request returns 403 through the proxy), so the image digest, its architecture list and its real `/etc/passwd` could not be read. Whether it is amd64-only (the VM is aarch64) was NOT checked.

## Why it was not built
- The runtime that produces the error is the ACI/LCOW guest (HCS on a Windows host, Hyper-V utility VM with GCS). It cannot run on the sandbox or on the Ubuntu aarch64 VM, and its strict behaviour no longer exists upstream.
- The original image is not obtainable here; it is an old CentOS 7 + WildFly image that needs a database, and an architecture mismatch with the VM is possible.
- The only buildable version is a teaching adaptation: our own strict passwd resolver in front of runc (a wrapper that reads `rootfs/etc/passwd` before `create`) and a small `USER 10001` image whose entrypoint adds the passwd line at start. It would test our own checker, not ACI, and not EJBCA; the screening note says this counts only as an adaptation.
- Coverage: q65393959 and q79297389 already cover identity resolution at exec time and a capability-limited caller. The new element is only "numeric USER missing from passwd at create time" and "fix it at build time with one unique uid/gid entry".

## If it is taken up later
Reopen only if (a) the strict guest can be run for real (a Windows host with LCOW and a 2020-era guest, or an opengcs build of that time; the fix commit that made `setUserID` fall back is in hcsshim between 0.8.12 and 0.9.0, not located here), and (b) the image can be pinned by digest and pulled (Docker Hub reachable, architecture matches).
Design if (a) and (b) hold: record that the image's rootfs has no uid 10001 while the entrypoint's passwd append has not run; show the creation failure on the strict runtime; allow an offline image fix that adds exactly one passwd line (and a group line) for 10001/GID at build time (`USER 10001` unchanged, not `USER 0`, no `whoami`-only output). Oracle on the real runtime: main process uid 10001, exactly one passwd entry for that uid with the intended gid, the health probe succeeds, data directory owner unchanged. If only the adaptation is wanted: label it in `task.txt` and the docs index as "strict-resolver stand-in", and reduce the target to a marker program instead of EJBCA.
