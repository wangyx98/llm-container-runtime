# q63433056 — "How to traverse through the pid namespace of a container?" (walk a paused runc container's process tree and make a chosen PID call clone) (isolation) — DEFERRED

## What the thread is about
One paragraph, no answers: in a runc environment the asker wants to walk the process tree of a PAUSED container and "call clone to a specific pid of that process tree so that it creates a new child process to it". Comments: Joseph Sible asks whether the asker knows how `ps` and `nsenter` work; the asker replies that the open points are how to call clone on a specific process while the container is paused, and how to run a custom (C/C++) program inside another namespace (nsenter with an object file says "file not found"). There is no accepted or any other answer, so there is no verified reference solution.

## Measured on 2026-11-01 (sandbox: x86_64, kernel 6.18, cgroup v1, runc 1.1.12)
- A bare runc container (static program, tree 579 -> 584 -> 585, PID/mount/IPC/UTS namespaces) was started and `runc pause`d. Traversal is easy from the host: `/proc/*/status` `PPid` and `NSpid` give the tree (e.g. `584 ppid=579 nspid=584 6`), `runc ps` lists the processes, and `runc list` shows `paused`.
- A frozen (paused) process cannot run anything: its state is `D`; `PTRACE_SEIZE` on it succeeds, but `PTRACE_INTERRUPT` does not make it stop within 3 s, and after `runc resume` it is `S` again. So "make the frozen PID execute clone while the container stays paused" is impossible as stated; the contract has to allow a temporary resume (and the paused state restored afterwards), or abandon "while paused". Not measured: cgroup v2 freezer (`cgroup.freeze`, the VM), where the same is expected.

## Why it was not built
- No answer and a one-line question: the whole contract (may the container be resumed for a moment, does the target cooperate, ptrace injection or a signal that makes it fork, what a "specific pid" is) would be invented by us.
- Coverage overlaps existing cases: `filesystem/q63752123` (a child with a chosen PID in the container's PID namespace through `nsenter -p` and `ns_last_pid`, NSpid read on the host) and `diagnostics/q63115522` (sibling/child relations under the shim, subreaper, reparenting). New would only be "a chosen EXISTING pid becomes the real parent of a new process" (plain `runc exec` cannot: its parent is runc or the shim) and the pause/freezer semantics.
- Cost: the reference solution needs a ptrace injector (`PTRACE_SEIZE`, get/set registers, write a `syscall` instruction at the instruction pointer, single-step, restore), with different registers and syscall numbers on x86_64 and aarch64; the VM is aarch64 and the sandbox cannot run arm64 binaries, so the first real check would be on the VM. About 4-5 hours.

## If it is taken up later
Contract (say it in `task.txt`): a runc container is paused; the solver may resume it for the shortest time needed but it must be `paused` again at the end; the target process does not cooperate; the new process must be a child (real PPID on the host) of the chosen existing process of the tree; the chosen PID is given as the PID INSIDE the container (random fixture tree of static programs, pids not guessable), and the container's init and the other processes keep their pid/start time.
Oracle: truth from the host (`PPid`, `NSpid`, PID namespace link, container membership by cgroup/NSpid); the new child has `PPid` = the host pid of the chosen process, is in the container's PID namespace (`NSpid` has two entries), `runc list` says `paused` at the end, the tree before and after differs only by the new child, and a process made by `runc exec` (parent = runc/shim) fails. Record the difference between ptrace injection and a cooperative variant (a signal handler in the fixture that forks). A traversal-only variant (PPid + NSpid of a paused tree) is a diagnostic adaptation and must not claim the clone request.
