# q76846815 — Docker image loses user file ownership when run on another machine (Ubuntu docker.io 20.10.25 built with Go 1.18) (filesystem) — DEFERRED after a time-boxed pre-study

Status: time-boxed pre-study (user, 2026-10-31); deferred by the user after it (2026-10-31). Nothing was built (no case files, test suite, fixtures or docs-index entries).

## What the thread is about
The asker builds images on an Ubuntu 20.04 host (docker.io 20.10.25-0ubuntu1~20.04.1, containerd 1.7.2, runc 1.1.7, `docker version` shows Go go1.18.1) from a RedOS 7.3 base (`pasaopasen/redos7.3`); the Dockerfile creates `groupadd -r -g 515 dreamdocs`, `useradd -u 2122 -g dreamdocs dreamdocs`, `WORKDIR /home/dreamdocs`, `USER dreamdocs`, `RUN touch file`. On the build host `ls -l` shows `dreamdocs dreamdocs`; on any other host (Fedora 36/37, minikube, Astra) the same image shows `root root` and the user gets `/home/dreamdocs/.bashrc: Permission denied`. Rebuilding on the other hosts works there. Constraint of the asker: the images must be built on that Ubuntu host and its packages may not be upgraded freely. Answers: (1) a pointer to Launchpad bug 2029523; (2) the asker: reinstalling Docker from Docker's own repository (24.0.5) fixed it ("the previous docker was a bit restricted").

## The cause, from the sources found (not reproduced here)
- Launchpad bugs 2029523 and 2029893; Canonical's fix "Fix docker layers ownership info in Focal" (docker.io-app PR #3, merged 2023-08-07): the Focal package 20.10.25-0ubuntu1~20.04.1 was built with `golang-1.18-go`; the fix 20.10.25-0ubuntu1~20.04.2 changes the build dependency to `golang-1.20-go` and puts `/usr/lib/go-1.20/bin` first in PATH (changelog: "Fix docker layers ownership info (LP: #2029523, #2029893)"). The Launchpad page (read through a summary) says the bug also affected Jammy (`~22.04.1`) and gives the mechanism as upstream code that is compiled only where the Go `unix` build constraint exists (Go >= 1.19), so a Go 1.18 build silently leaves out the part that puts the numeric uid/gid in the archive; this mechanism is second-hand and was not verified in the source.
- moby issue 46161 (closed as an Ubuntu packaging problem): with the legacy builder a `chown` in one `RUN` is gone in the next `RUN` on Ubuntu `docker.io` 20.10.25-0ubuntu1~22.04.1; not on 20.10.21-0ubuntu1~22.04.3, on upstream 20.10.24 or on docker-ce 24.0.5. The thread does not test export, save or push.
- So the stated "root cause cannot be confirmed from a reinstall" worry is answered by the distribution's own fix (same version number, only the Go toolchain of the build differs).

## Why it was not built
- The defective engine cannot be obtained in the sandbox: launchpad.net, api.launchpad.net, launchpadlibrarian.net and archive.ubuntu.com / ports.ubuntu.com are refused; the Ubuntu pool of a public mirror (checked on mirror.seas.harvard.edu) no longer holds `docker.io_20.10.25-0ubuntu1~20.04.1` or `~22.04.1` .debs (superseded binaries were removed; only 20.10.21 and later 20.10.25+dfsg builds are there). Only Launchpad's own file store could still serve them; nothing was checked there. `download.docker.com` is reachable (static 20.10.25 from upstream, built with a newer Go) and could serve as the healthy counterpart, but not as the defective one.
- No Go 1.18 toolchain: go.dev and proxy.golang.org are refused; the sandbox has Go 1.24.7; building a patched moby 20.10.25 that leaves out the `unix`-constrained files would be a stand-in for the defect (heavy and not the real artifact).
- The original images (`pasaopasen/redos7.3`, `pasaopasen/docutable-test-perm`) are on Docker Hub; the sandbox cannot reach its token host (auth.docker.io), and a personal repository from 2023 may be gone. An offline base with a shell and user tools would have to be built instead (e.g. the VM's own busybox-static).
- Without the defective engine nothing can be measured about candidate fixes (BuildKit instead of the legacy builder, a healthy engine, re-creating the layer tar by hand), so the set of valid alternatives for an oracle cannot be fixed. The thread's own fix (reinstall Docker) contradicts the asker's constraint.
- Coverage: no existing case looks at ownership recorded in image layer archives; but the defect lives in one distribution build, already fixed in every supported release (apt on the VM installs the fixed package), so the environment does not reproduce it by itself, and the case would depend on a pinned old .deb that is no longer in the archive pool.

## If it is taken up later

If it can: private dockerd extracted from the defective .deb (data-root and socket of the case, the machine's Docker untouched) next to the static upstream 20.10.25; offline base from busybox-static (RUN with adduser/touch/chown); legacy-builder build of the asker's four steps; measurement: numeric uid/gid in the layer tar of `docker save` from each engine and in the extracted rootfs (UID 2122 / GID 515 for /home/dreamdocs/file; the defective engine gives 0/0). Candidate task: "rebuild the image so that the saved layer carries 2122/515, without chown after start and without upgrading the lab's defective engine"; oracle: compare the layer tar entries of the image (not the running container), run the image as 2122 and write its own file, engine files unchanged. Do not build before the defective .deb is really in hand.
