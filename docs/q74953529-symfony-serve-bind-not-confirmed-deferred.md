## The loopback-bind hypothesis and why it fails for the original (measured 2026-10-31)
Symfony CLI binaries from the GitHub releases (linux amd64) were run in the sandbox with php-cli 8.3.6 and the listening sockets read from `/proc/net/tcp`:
- CLI 5.4.19 (released 2022-11-19, the version `get.symfony.com` installed in Dec 2022): `symfony serve` listens on `0.0.0.0:8000` (all interfaces).
- CLI 5.12.0: listens on `127.0.0.1:8000`; with `--allow-all-ip` it listens on `0.0.0.0:8000` (`--listen-ip` default `127.0.0.1`). The CLI warns: "the Symfony CLI only listens on 127.0.0.1 by default since version 5.10.3".
So with the asker's CLI the server was reachable on the container's own address and a published port would have worked on Linux; the "application only listens on the container's loopback" explanation belongs to the current CLI, not to this thread. Cause of the original failure: not determined (candidates: Rancher Desktop / Lima port forwarding on macOS for nerdctl-compose ports, a compose publish that did not take effect (`command: php` overrides the image command), the TLS/proxy layer); none can be checked from the post, and the macOS VM layer cannot be reproduced on the Linux sandbox or VM.
