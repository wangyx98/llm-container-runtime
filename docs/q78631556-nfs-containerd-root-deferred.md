# q78631556 — containerd root on an NFS share: "failed to convert whiteout file ... .wh..wh..opq: operation not supported" (filesystem) — DEFERRED

Status: deferred by the user (2026-10-24); re-examined as "conditional build" on 2026-10-31, a VM probe was tried, and the case stays deferred (decision 2026-10-31). Nothing was built (no case files, test suite, fixtures or docs-index entries). The probe script is kept in the project as `case-notes/q78631556-nfs-probe.sh`.

## What the thread is about
The asker moved containerd's root from /var/lib/containerd to an NFS mount (/var/nfsshare/containerd). `ctr` pulls `registry.k8s.io/kube-apiserver:v1.28.11` and fails while unpacking a layer: `failed to extract layer sha256:0110...: failed to convert whiteout file \"usr/local/.wh..wh..opq\": operation not supported: unknown`. The only answer: overlayfs works only on supported base file systems and NFS is not one of them. No fix is given.

## Mechanism (inferred, NOT measured on NFS)
For the overlay snapshotter containerd turns an opaque whiteout marker (`.wh..wh..opq`) into the extended attribute `trusted.overlay.opaque=y` on the directory, and a whiteout file (`.wh.NAME`) into a 0/0 character device. An NFS client has no handler for the `trusted.*` xattr namespace (NFSv4.2 only has `user.*`), so setxattr returns EOPNOTSUPP. With root_squash, `mknod`/`chown` may fail with EPERM before that step. An overlay mount with upperdir/workdir on NFS is refused anyway, so "everything on NFS and still the overlay snapshotter" has no working path. Plausible boundaries of a fix: (A) keep the overlay snapshotter's root on a local disk (`root_path` of the overlayfs plugin) and leave the content store and metadata on NFS (bolt on NFS is a risk: flock/mmap); (B) use the native snapshotter on NFS (applies whiteouts itself, copies layers; needs no_root_squash for chown); (C) all on NFS with the overlay snapshotter: no feasible path, not to be included.

## Sandbox facts (re-checked 2026-10-31)
Kernel 6.18 without nfs/nfsd (`/proc/filesystems` has none, no /lib/modules, `mount -t nfs` says unknown filesystem type, no nfs-kernel-server in apt). Every file system the sandbox has takes `trusted.*` xattrs and 0/0 whiteouts, so no local file system reproduces ENOTSUP; a FUSE file system that refuses the xattr would only simulate the errno. The NFS part can only be tested on the VM.

## VM probe (2026-10-31): what was learned
The probe (`case-notes/q78631556-nfs-probe.sh`) builds loopback NFS exports (4.2 and 3, root_squash and no_root_squash), tests which operations each accepts, and runs containerd 1.6.21 (pinned) on nine backing/snapshotter combinations with an offline two-layer image (opaque directory + whiteout). First run on the VM (Ubuntu 22.04.5 aarch64, kernel 5.15.0-198-generic, cgroup v2): `nfs-kernel-server` and `nfs-common` (nfs-utils 2.6.1) installed and the server was active, so the kernel has the nfs and nfsd modules (the precondition for a case is met). No NFS measurement was obtained, for two harness reasons, not NFS reasons: (1) `/etc/exports.d` does not exist after a fresh install, so the export file could not be written and all four mounts failed with `access denied by server`; the measurements then ran on plain ext4 directories (the probe now creates the directory and stops if a mount is not NFS); (2) the download of the containerd tarball into `/tmp/probe78631556` died with `curl: (23) Failure writing output to destination` (cause not determined: the sandbox copy of the VM's disk shows 78% used; the probe now prints `df` on a failed download). The fixed script was not run on the VM again.

## Why it stays deferred (cost against what a case adds)
- Everything that matters is VM-only: the sandbox cannot show one NFS result, so a built case would meet real NFS for the first time on the VM, with several round trips (root_squash can turn the thread's symptom into a different error; loopback NFS has deadlock risks under memory pressure; bolt on NFS is unknown).
- A case needs the VM's system state changed: package installation, an NFS server running, `/etc/exports.d` entries, loopback mounts. Cleanup can remove exports and mounts, not the service or the packages.
- The fix space is narrow and mostly configuration (overlay `root_path` local, or `snapshotter = native`); the NFS-specific fact (the backing file system refuses `trusted.*`) is not visible in a solution text and the thread has no accepted fix, so a model can reach a passing answer from the single-sentence answer plus general knowledge. The new coverage dimension (snapshotter backing file system) is real but small next to the cost; q58642878 already covers moving containerd's root onto another disk with dynamic checks.
- Coverage: no existing case has NFS or whiteout/opaque handling; closest are `diagnostics/q77179505` (which image is behind an overlayfs snapshot directory) and q58642878 (root moved to an external disk).
